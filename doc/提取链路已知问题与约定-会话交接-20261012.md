## 2. 用户最新确定的业务约定

以下以用户 2026-10-12 的说明为准，不能再用当前实现反向定义需求。

### 2.1 最终结果层级与任务二节点

最终抽取 JSON 应表达：

```text
公告级
├─ 项目编号、项目名称、项目总金额等
└─ 包列表
   ├─ 包1：包级字段、cobs、subs
   ├─ 包2：包级字段、cobs、subs
   └─ ……
```

- 同一公告中的不同包彼此独立。
- 任务二关系图中，每个包拥有一个独立的项目节点。这是图中的身份粒度，不意味着最终 JSON 应删除公告级外层。
- 当前代码的 `Project` 实际代表一个包，`project_id` 在运行中由项目名称与包号构造。数据库还有 package_key、round_no 等入库身份处理，不能把运行期键与数据库最终键混为一谈。
- 最终公告级输出、包级结果、关系图每包一个节点可以同时成立，不要求因此重构全部数据库表。

### 2.2 候选

- 候选是已抽取但尚未经过 delta 决策的 COB/SUB 观测。
- 一条候选不等于一条最终 COB；同一对象可有多条跨文件、跨表观测，同名候选也可能代表不同成交明细。
- 候选应保留包归属、字段状态与来源证据。缺名的成交观测应保留供后续补名，不能因为缺名就提前丢弃，也不能擅用项目名称填名。
- 模型负责判断重复、独立明细、对象粒度与字段归属；程序依据其合法决定执行、计算和审计。

### 2.3 金额

- **公告级金额只从 HTML 抽取。** 附件中看到的项目总预算不能塞进包金额，也不能作为新的公告级业务金额输出。
- 包级金额、COB 金额、SUB 中标金额必须有各自明确的归属与承载位，不能共用含义模糊的 `total_price`。
- 预算、最高限价不等于最终中标成交价格；应在模型抽取时明确边界，而不是用关键词规则事后硬删。
- “金额层级”与“金额性质”是两个维度：公告/包/标的/供应商归属，与预算/限价/中标成交等不能混作一件事。
- 单包只有一个 COB，不自动证明包金额就是该 COB 总价。此前用户允许模型明确确认整体成交对象后引用包金额；这种有证据的取值应与随意混放金额区分。
- 程序可以计算，但计算依赖、所用字段及原文来源应记录；计算值不能伪装成原文直接观测。

### 2.4 校验与重试

- 校验必须匹配当前模型输出 JSON 的契约，不能用旧字段集合或旧粒度否决新版合法表达。
- 用户原定重试用于模型输出结构或协议错误，例如缺少必需键、类型错误、非法枚举、非法引用。
- 金额不一致、原文字段不可用、来源冲突属于业务问题，应交给模型取舍或保留未决；不能统称为 JSON 结构错误并要求完整重抽。
- 校验器与新版契约不一致属于实现问题，不应归咎于模型输出不合法。
- 不重试业务冲突不等于绕过执行约束：未知引用、重复计数、供价资格绕过、无效依赖仍应阻止执行。
- 对相互依赖的 delta 计划，不能为了接收部分操作而破坏依赖或重复计数保护；对独立输出通道的接收边界，则需要单独设计。

### 2.5 字段否定与计算

- 否定候选 `c:…` 的某字段：该来源字段不可供值，不意味着最终字段必须空，可从其他可靠来源或计算取得。
- 否定最终组 `g:…` 的某字段：最终明确置空，后续不能自动补回。
- 采用和未采用必须按同一粒度表达和比较。既然允许逐字段取值，就不能仅凭 candidate_id 判断整条候选是否“已采用”。

- 品牌与产品供应商均存在时，任务一优先展示品牌；缺一方时可按赛题确认口径互补展示，不覆盖两个原字段。

当前 `Candidate` 分为：身份(candidate_id/entity_type)、归属(project_id/package_no/binding)、字段(fields)、来源(source/evidence)。

## 5. 已知冲突：来源、原因与影响

### P01：字段级取值与候选级计量解释冲突

**证据：原产物证实；中卫及相关计划做过离线复核。**

位置：`src/ict/merge_protocol.py` 的 compile_plan/accounting 与 materialize；当前约 261–350 行。

模型可以只采用候选 A 的单价/数量，不采用其总价；执行器却以 candidate_id 记录已采用，再用 candidate_id 检查 quantity_accounting。reason 虽说明“只是总价未采用”，程序不会按中文理由拆分字段。

已见：中卫 `t20260206_26155241` 包2；甘孜 `t20260202_26141964` 两包；德州 `t20260602_26668587` 两包；口腔 `t20260206_26154814` 包5。

例如德州模型显式 price_from 附件的 unit_price、公告的 quantity/unit/total_price，并说明附件数量/总价重复；该组合可以自洽，却遇到整候选已采用/未采用冲突。

根因不是金额总和不等于包金额，是解释与采用记录的粒度不一致。修订方向尚未实施：采用/拒绝/未采用必须能够定位候选及字段。

### P02：空单位也让旧默认候选被记为已采用

**证据：用原回答离线复现。**

案例：`t20260202_26140146` B包，济宁市第二人民医院信息化能力提升采购项目。

离线 materialize 抛错时的实际局部状态摘录：

```json
{
  "values": {"unit_price": 400000.0, "quantity": 1.0, "unit": null, "total_price": 400000.0},
  "origins": {"unit_price": "c:cand_000012", "quantity": "c:cand_000012", "unit": "cand_000005", "total_price": "c:cand_000012"},
  "used": ["cand_000005", "cand_000012"]
}
```

来源：该例 08 候选、08b 证据、model_trace 中本包第一次回答。代码位置：`merge_protocol.py` 约 328–336 行，在未显式绑定字段存在默认来源时，无论实际值是否为空，都加入默认候选。

影响：cand_000005 没贡献非空计量值，却触发“已采用计量观测不能同时标为未采用”。这是独立的执行记录问题，不能全部归为模型解释协议不足。

### P06：附件包金额未进入统一归属组件

**证据：代码确认；不意味着本轮每条附件金额实际归错。**

位置：`pipeline.py` 附件后 bind_packages 调用；`src/ict/bindings.py`。

附件新候选送入 bind_packages，但独立 package_amounts 未作为输入传入。组件金额输入包括既有包金额、公告 summary_amount、COB 候选 total_price；附件包金额仍由第 8 步按它自带的包号查找。

因此“所有附件金额已统一复核归属”的说法不准确。金额列表与候选不是不能分开，而是最终归属裁定必须明确并可追溯。

### P07：SUB 金额没有字段，模型输出被静默裁剪

**证据：原回答与保存候选逐项比对证实。**

位置：`src/ict/config.py` 的 SUB_FIELDS 目前仅 supplier_name/score/is_winner；`src/ict/candidates.py` 约 118 行只接收集合内字段；`schemas.Sub` 最终也无金额。

案例 `t20260303_26212365`，包4，模型原回答相关字段如下（省略其他字段）：

```json
{
  "entity_type": "sub",
  "package_no": "4",
  "source_refs": ["html:t3:r0"],
  "fields": {"supplier_name": "广州健星仪器有限公司", "total_price": "189,600.00元", "is_winner": "是"}

```

保存的 `03_html_candidates.json` cand_000004 仅有三个 SUB 字段；189,600.00 元仍在 evidence.row_text，却没有独立金额字段。对应原始调用 call_id：`c64e632e481745fdbfffc5eb0cacdaf1`。

这不是“模型漏抽”，也不是结构重试，是输出字段与接收集合不匹配。该数究竟表示包金额还是供应商中标份额，要明确裁定，不能沿用 COB total_price 或直接删掉。不得据此擅自把每个供应商金额都复制成包金额。

### P08：金额性质与层级的字段表达不统一

**证据：代码/字段定义确认；缺失性质导致错误供价的具体实例不能一概断言。**

- 公告 Amount 有 scope（announcement/package），没有同形式的 amount_kind。
- 附件 PackageAmountObservation 有 amount_kind（award/budget/unknown），没有公告级 scope，package_no 必填。
- 附件 amount_kind 缺失时，校验、封装默认 award。
- bind_packages 的“只引用 award”检查主要检查模型返回的 amount_kind；输入 amount_observations 没有统一携带已裁定的性质，所以不能把它理解成独立证明来源确为成交价。

性质需要模型明确判断并保留，不能靠默认 award 或根据单个金额值猜。最高限价在抽取时误入 COB total_price 的问题见甘孜案例。

### P09：否定来源总价后的再计算没有衔接

**证据：代码确认；中卫原计划离线去除冲突解释后可执行，但总价仍为空。**

位置：`s07_normalize.py` 约 111 行；`merge_protocol.py` fields_reject/materialize；`s08b_repair.py` 约 65、117–138 行。

第 7 步在 total_price 非 present 且单价/数量有值时计算；若已有总价，仅记录不一致。第 8 步后来否定总价，并不重新运行第 7 步。8b 只有特定 overflow 备选修复路径内会乘法补全，v4 正常计划不生成旧 alternatives。

故修好校验不等于中卫自动得到 76800。需要明确字段选定后的计算时机、依赖来源和最终禁止推断状态。候选来源被否定与最终组字段被否定必须分开。

### P10：结构错误、执行约束和业务冲突共用一个重试出口

**证据：调用链与日志确认。**

`complete_json(validate=…)` 只接收错误文字。第 8 步 validate 内同时 compile_plan 和 materialize，JSON、引用、顺序、计算资格、计量说明冲突等统一进入重试。

这没有实现用户原定的错误分类。需要区分响应结构错误、无效计划依赖、业务证据冲突、校验器不兼容。不能取消所有校验，也不能无条件接收非法计划。

特别注意：`s08_merge.py` 还留有旧 `_validate_merge`、旧 delta 执行器。**在线 v4 校验实际使用 `_ask_merge` 内的 compile_plan/materialize；旧基线仅在无模型或回退路径生效。** 不要只修改旧函数就宣称解决在线问题。

### P11：公共最终 JSON 缺公告级外壳

**证据：代码及 projects.json 确认。**

`pipeline.py` 约 258 行直接将每包 Project 转成数组输出，公告字段另存在 01、有效理解及数据库 announcement 中。数据库已有 summary_amount_yuan，不能误说公告总额全链路都丢了。

与用户当前最终 JSON 约定不一致的是对外结果封装。任务二每包一个项目节点是正确设计，不应连带改成整个公告一个项目节点。

### P12：COB 总价说明与包金额供值例外不一致

**证据：提示词/字段定义确认；不能据此断言 A 包空 delta 的唯一原因。**

`fields.py` total_price 写“整包或整项目的总金额不算它”；`merge-objects-v4.md` 又允许 package_amount_bindable=true、最终单组且整体成交对象对应明确时使用 p:amount。

需说明禁止混放与有证据的取值转换之间的边界，保持唯一语义。A 包空 delta 的模型内部理由没有记录，见第 8 节。

## 12. 后续定位与验证边界（非新增实施授权）

建议解决顺序是依赖说明，不是已批准实施计划：

1. 固定公告/包/COB/SUB及金额承载契约，明确模型实际输出、封装对象和最终输出的对应关系。
2. 对齐逐字段取值、未采用说明、拒绝语义；修复空字段误记used的执行记录问题。
3. 区分结构错误、计划执行约束、业务冲突及实现不兼容，确定独立输出接收与重试修复的范围。
4. 连通已发现证据、原生抽取、页定位、合并的状态；让附件金额进入一致的归属裁定。
5. 明确字段选定后的计算及依赖审计，最后对齐公告级公共结果封装。

验证应优先离线复用真实回答，分别证明：

- 中卫只拒绝错误来源字段后，其他有效取值不会被候选级校验误拒；最终禁推断字段仍不会复活。
- 济宁B包空unit不再让无贡献候选进入已采用集合；重复观测不会重新累加。
- 顺义某金额项错误不会导致独立合法名称静默消失；其已发现的证据有明确处理状态。
- 不同单价灯具仍两条、台/个终端仍分组，不通过新的同义规则相加。
- 未知编号、重复叶子、失效组引用、无资格供价等非法计划继续被阻止。

离线验证只证明实现语义。真实提取效果需要在用户允许、服务器就绪后再调用模型/OCR验证；没有新跑数、金标对齐及可比基线前，不给准确率提升结论。
