# 简单账号与数据隔离

2026-10-15，用户要求补全基础注册登录，并将全量结果归入赛题测试账号，尽量减少表结构变化。此改动仅涉及身份、持久化作用域、任务调度和界面，不调整抽取规则、提示词、OCR、包归属或供应商缺口关闭策略。

## 界面和会话

`/login`提供用户名/密码登录与注册切换，注册时确认密码；无邮箱、短信、验证码、人工审批或额外身份步骤。用户名3至32位，密码6至128位，不要求字符种类组合。注册后自动进入自己的空数据空间。顶部显示用户名并提供退出。

密码以独立随机盐和PBKDF2-HMAC-SHA256（600,000次）存储，不保留明文；算法参数参考[OWASP密码存储建议](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。会话使用随机Cookie，数据库只保存token摘要，7天失效；Cookie为HttpOnly、SameSite=Lax，退出或重置密码撤销会话。HTTPS部署设置`ICT_COOKIE_SECURE=1`。

登录/注册/退出的状态变更检查浏览器Origin，前后端走同一站点；Vite保留原Host，nginx传递`$http_host`以保留端口。API不再开放通配跨域。未登录业务接口返回401，跨账号具体对象及任务返回404。`/api/ping`是无需登录的存活检查，`/api/health`的资料库计数和版本需要登录。

前端路由在进入业务页之前确认会话。登录、退出使用完整页面导航，清空旧账号的星图快照、查询和页面内存；同浏览器其他标签通过不含凭据的变更通知重新确认会话。Cookie不写localStorage，登录凭据也不写浏览器持久存储。下载仍通过同源Cookie鉴权。

## 最小表结构变更

通过`db/002_accounts.sql`迁移，`001_schema.sql`作为旧基础结构保留。新空数据卷按Compose中的两个挂载SQL先后初始化；已有数据卷需手工执行002，不能指望重启容器自动迁移。

| 对象 | 变化 |
|---|---|
| app_account | 新表：账号、用户名、密码摘要、独立tenant_id |
| app_session | 新表：会话摘要、所属账号、到期时间 |
| announcement | 复用现有tenant_id，主键由公告ID改为(tenant_id, announcement_id) |
| project | 仅增tenant_id；公告外键改为(tenant_id, announcement_id) |
| supplier | 仅增tenant_id；名称唯一性改为(tenant_id, norm_name) |
| cob、bid、winner_coop_supplier | 不新增列，通过project/supplier关联隔离 |

旧default数据的公告ID、project_id、金额和raw_json不重写；project与supplier归属在迁移中补齐。非default账号新入库的数据库采购单元业务键加账号命名空间；原抽取文件及官方UUID不加前缀。不同账号上传同一公告不会覆盖，轮次规划、覆盖删除和无引用供应商清理都限定在本账号。

全部业务SQL经`server.db.q`统一添加当前账号的作用域CTE，包括嵌套查询、五类场景、底图、补载、统计、档案、详情和导出；原SQL视图的结果也按本账号项目限定。账号会话读写使用单独入口。此方案属于应用层权限边界，数据库管理员仍能访问全部数据，不宣称使用了PostgreSQL RLS。

## 上传、runs和worker

API的tenant只来自服务端会话，不接受请求JSON或URL指定账号。任务、原件和runs分别位于：

```text
<ICT_DATA_ROOT>/jobs/<tenant_id>/<job_id>.json
<ICT_DATA_ROOT>/tenants/<tenant_id>/incoming/<job_id>/
<ICT_DATA_ROOT>/tenants/<tenant_id>/attachments/<announcement_id>/
<ICT_DATA_ROOT>/tenants/<tenant_id>/runs/<announcement_id>/
```

查询进度只读取当前账号目录，不回落到其他账号或开发目录。旧default目录不用移动。

仍只启动一个`python -m ict.worker`进程；它显式扫描所有账号任务，并把每个任务的tenant传递到读文件、提取产物路径和入库。线程数仍由既有参数控制。锁位于jobs根目录，避免每个账号各起一个worker让模型并发翻倍；新worker也检查旧版账号目录中仍存活的锁。

入库成功后仍清理HTML/ZIP和解压附件，保留runs及jobs；失败保留原件。partial沿原worker语义入库并清理，未在此修改。重启中断修复也扫描所有账号，不从中间步骤自动续跑。

## 已部署v1.6/v1.8服务器的升级顺序

以下以`/root/workspace/ICT`、库名`ict_prod`为例，实际路径和库名先核实。先暂停上传、排空任务，停止API与worker，备份数据库和完整运行目录；数据库容器和数据卷继续保留。

1. 更新到包含账号改动的同一个前后端提交，保留生产.env、品目目录、运行数据和原数据库配置。
2. 在目标库执行迁移；不要重复执行001，不使用清库重建。

   ```bash
   cd /root/workspace/ICT
   docker exec -i ict-pg psql -U ict -d ict_prod -v ON_ERROR_STOP=1 < db/002_accounts.sql
   ```

3. 创建赛题账号，或将一个已注册的空账号绑定到旧default。下面两种方式任选一种。

   **旧数据已全部位于default，直接创建对应账号：**

   ```bash
   .venv/bin/python -m server.manage_accounts create --username contest --legacy-default
   ```

   密码交互输入两次，不在命令行、代码或说明中预设公共密码。账号名可自行替换。该操作绑定数据空间，不移动文件、不重跑提取。

   **账号已经从网页注册、尚无数据或任务：**

   ```bash
   .venv/bin/python -m server.manage_accounts bind-legacy --username contest
   ```

   旧default只能归一个账号；已有数据/任务的账号不自动合并。绑定后旧会话撤销，重新登录。普通网页注册不能指定或认领default。

4. 如果全量尚未提取，直接登录赛题账号上传，worker自然把新结果放入该账号；其他新注册账号保持空数据空间。手工导入runs时，`db/load_runs.py --tenant`填写该账号tenant_id，绑定default的账号则用default。手工导入只写数据库，不自动复制runs，需同时安排运行目录。
5. 更新依赖、重新构建前端并发布至原静态目录；核对nginx保留原Host。API与worker继续使用同一`ICT_DATA_ROOT`、同一数据库。
6. 按数据库→OCR/SSH隧道→API→页面检查→worker顺序启动。worker启动会领取所有账号既有排队任务，应先确认队列。

   ```bash
   sudo systemctl start ict-tunnel ict-api
   curl -fsS http://127.0.0.1:8000/api/ping
   curl -fsS http://127.0.0.1:6008/health
   # 网页登录并检查后：
   sudo systemctl start ict-worker
   ```

服务器端重置密码：

```bash
.venv/bin/python -m server.manage_accounts reset-password --username contest
```

重置会撤销该账号原会话。前端没有找回密码流程，不引入短信或邮件。

已迁移数据库后不可只回退旧版代码：旧版全局公告ID冲突目标已不适用，且没有登录权限边界。完整回退应恢复匹配的数据库、运行目录、后端和前端备份。
