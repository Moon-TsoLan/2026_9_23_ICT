# 附件抽取与结果树合并设计讨论稿

## 2026-11-17 开发顺序与流程修订

本节为 11 月 17 日更新；下文保留扩大样本核对前的讨论记录。用户已要求优先实现文件三分类、采购单元合并和第三类定向补空。

1. **HTML 建树。** 概要与剩余正文独立读取并保留具体来源。按对象、字段及金额性质消歧；真实冲突保留双方原值，单侧有依据的事实先入树。已知采购单元下挂 COB、SUB；不能归包的独立观测暂挂虚单元，同一供应商的多笔金额、得分分别保留。结构暂不完整仍可向附件提出 needs。
2. **可用性与三分类。** 依实际格式读取，排除确实打不开、加密不可读、空容器和实际为下载错误页的文件，仍可用的页或成员单独保留。纯图像可读。先用文件名、原生正文和表格判定：本案已填结果、报价、评审或提供关系优先归第一类；采购文件、带采购信息的未填模板归第三类；只有身份、业绩、报酬等用途的材料归第二类。仅看出文种或标题且填报区域不可读时保持不确定。需要时把低精 OCR 文本按原位置加入同一判定器，再判不出就跳过。本轮分类算法和分类评估离线执行，区分需要 OCR、无用与来源损坏。
3. **冻结前半程。** 用固定公告建树、对照已复核附件检查分类，将真实包、虚单元、候选和文件决策固定下来；用同一份输入测试后半程。第一类最终按整文件交给抽取模型，图像正式读取走远端 PaddleOCR。长件成本参考跨案例核对，不以两万字作为上限。
4. **采购单元合并与包内 delta。** 模型根据本案 HTML 和第一类事实判定虚分支归属及简称/全称指代，程序执行对已知引用的决策。无依据就不绑定；没有归位的虚单元不出业务行。重点观察 t20260309_26250037 两个虚单元是否按证据分别归位。包内 delta 优先复用现有 COB、SUB 模块。
5. **第三类定向补空。** 包内合并后只针对已知对象的空字段就地查找。按标签、章节或表头及同行关系取项目身份、原包号与正式包名、COB 品目；成交材料明确指向该清单且同一对象和口径可确认时才用明确的规格、计价数量。无法区分候选就保留缺口；不抽新对象或成交价。先单独测本地查找效果，再讨论是否启用同会话多轮模型。
6. **最终定稿设计。** 有明示最终值时保留原值；合计补包金额须同时确认覆盖整包、无重复、同一计价口径及最终报价阶段。保留两项既定 SUB 默认政策及冲突阻断；来源记录注明直接值、推算或政策补值。取消独立修复步骤中的凑价改选和中标人自供推断。最终三表与装载取同一定稿结果。本轮优先模块开发不包含数据库迁移、部署或重写定稿环节。

### 本轮实际接通的入口与实测

开发入口依次为 `python -m ict freeze-front 公告ID 前半程.json`、`python -m ict merge-units 前半程.json 归包.json`、`python -m ict package-delta 归包.json 包内合并.json`、`python -m ict fill-reference 归包.json 包内合并.json 补空后.json`。各步输出须指定新路径。第一步调用模型读取两路 HTML，随后离线分类；第二、三步调用配置的合并模型；第四步纯本地运行。已有首判图像文件的识别文字时，可给第一步传 `--ocr-json 文件.json`，格式如 `{"扫描件.pdf":{"1":"第一页识别文本"}}`，仅在首判待 OCR 时使用。本轮没有接入在线 OCR、第一类全文抽新行、最终定稿和入库。冻结文件保存原生页和参考表格，方便后半程反复重放。

## 2026-11-16 讨论原文

2026-11-16。应用户要求，在扩大样本核对前记录本轮讨论。以下区分当时用户确定的流程与助手提出的实现取舍。字段含义见[三表口径](任务目标与最终字段口径.md)，已核实的旧流程问题见[错误记录](附件抽取错误记录与重设计边界-20261116.md)。

## 一、HTML 与初始结果树

独立提取公告概要表格和剩余正文，消歧后建立项目、采购单元、成交标的（COB）、投标响应主体（SUB）的结果树。项目层保留名称、原项目编号、采购单位、分包/标段情况与公告品目。包层保留原文类型、编号、名称及包金额。对象字段沿用 `src/ict/fields.py`，原文明示属于某供应商的成交金额跟随 SUB，和投标报价、包成交额分别处理。

归属待定的 COB 或 SUB 可由内部虚采购单元挂载。原文已确认的供应商、成交额、得分等关系一起保留。真实未分包和未知包归属分别表达。第一轮 needs 覆盖已知对象的字段缺口、归属问题，以及可能新增的 COB 和 SUB。

**建议的 HTML 消歧口径**：同值或单侧有值且指向同一对象、同一性质时合并。公告总额、包成交额和供应商金额各自挂载。两路异值时先看原文标签和对象，证据不足则保留来源并交后续合并，避免一律偏向正文或按序号猜归属。

## 二、附件分类与第一类抽取

1. 首次以文件名和原生文字、可读表格结构进行规则分类。此次不考虑图像。无法判断才检查有无图像，有图时调用低精 OCR，再将原文与识别文字交同一个分类器。无图可补或二次仍无法判定，直接跳过。这是用户接受的复杂度与漏读取舍。
2. 第一类为直接提供本案成交、响应、明细或归属事实的材料，包含《中标结果公告》。按文件全量输入模型，图像内容用远端 PaddleOCR，按原序保留表头、明细、合计和签章。文件可以涉及多个包，也可以只证明一项关系。抽取结果作为已有项目的待合并分支。
3. 第二类为主要只有身份、资格或承诺且缺少本案目标信息的材料，跳过。第三类为主要描述采购要求、目录与投标模板的文件，留待结果树合并之后处理。文件名、篇幅和单个表头均不足以定义类别。
4. **建议的规则组合**：封面/主标题与章节结构支持招标文件身份时，内嵌报价或声明模板随整份文件归第三类。结果性标题与已填写的主体、报价、得分、标的行等关系支持第一类。声明标题与身份承诺正文支持第二类；若有本案标的和具名制造商的填写关系，按第一类考虑。这些是分类假设，尚未验证为普遍规则。
5. 低精 OCR 使用用户提供的 DeepSeek OCR 文档与当前配置。分类用 `POST /v1/tools/ocr`，multipart 字段为 `file` 和 `purpose=text_recognition`，读取逐页文本。API 不支持页码参数，提交单图/图像页与提交整本文件是不同计费范围。识别失败与无法分类分别记录。低精 OCR 服务于分类，第一类正式提取按上项走远端 PaddleOCR。

## 三、采购单元合并、包内合并与收尾

1. 合并比较前规范化原文值，如金额和表头单位、数量与计价单位，保留来源。采购单元合并由模型看 HTML、第一类附件和相关分支判断归属，程序执行。处理虚单元归位及包简称/全称。剩余虚单元忽视，不作为真实包入库；助手建议利用已有未归属记录保留线索。
2. 在各真实采购单元内做 COB、SUB 的 delta 合并并补字段。用户提出缺失包金额可由所属 COB 总价合计；助手建议限于明细覆盖整包、同一成交口径且去重后再推算，区分原文明示与推算，避免汇总行和分项重复相加。
3. **第三类补全的最新讨论方向**：用户提出用灵活本地查找替代模型。助手建议由程序枚举已有对象中适用的空字段，有缺口才在第三类现成原生文本/分类 OCR 文本中定位。项目名称、编号取项目明示标签；包编号与包名称取同行明确列或标题；标的名称与包名区分；品目需对应已知对象；规格、数量需已有成交材料指向清单并能确认口径。普通服务范围、最低技术要求、预算、限价不回填成交字段。多值无法消解或原文不足就留空，不新增对象。此建议省去原设想的间隔目检与多轮页段问答；实际边界仍待核对。
4. **建议的旧收尾取舍**：保留合并前格式规范化和既有最终 SUB 政策；保留一致性问题报告，取消独立的金额修复改选及事后推断中标人自供。单价乘数量等推算与格式规范化分开处理。最后适配现有三表与数据库，沿用账号隔离和合并接续调度。

## 模块对应

HTML 入口为 `steps/s01_understand.py`；第一轮 needs 在 `steps/s03_plan.py`；文件分流、原生读取及全文抽取涉及 `steps/s04_attach.py`、`attachment_pages.py`。第一类全文交付不能走旧顺序截断与逐页字符切块。规范化、归包、对象合并分别对应 `steps/s07_normalize.py`、`bindings.py`、`steps/s08_merge.py` 与 `sub_merge.py`。第三类本地查找的位置在包内合并后、最终适配前。旧收尾取舍涉及 `steps/s08b_repair.py`、`steps/s09_supplier.py` 和 `supplier_policy.py`。上述均由 `pipeline.py` 编排。

原讨论的两个例子为 `t20260309_26250037`（两包中标人待归属、结果公告和报价签章可解）与 `t20260206_26154828`（第 4 物理页列的是包号与标的名称）。扩大样本核对的观察另见[案例分析](../eval/附件重设计跨案例核对-20261116.md)，以便区分原设计与后见发现。
