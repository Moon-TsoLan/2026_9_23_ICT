# 第 8 步 标的合并规范（v5，已实施）

日期：2026-10-04。状态：**已实施**，`pytest tests` 74 passed。v3/v4 草案归档在
`doc/archive/第8步标的合并规范-v3v4-已作废.md`。

v3 把两行之间的关系穷举成 `EE/NE/AO/NN × T/F/X × s/d`，算术与取值那半部分是好的，本文保留；
但它的同一性判定建立在"先按规范化名称分组，不同名称的行天然不相干"上，这一条在真实数据上不成立：
破折号被 OCR 成一个「一」字就整条丢弃，公告写「智能建造设备」而附件写「建筑增材制造设备（3D混凝土打印机）」
也整条丢弃。反过来同名也不等于同物（同一则公告里三行都叫「智能建造设备」，是三个标的）。

所以 v5 换了一个分界线：**同一性是内容判断，交模型；算术与来源资格是结构事实，归规则。**

---

## 1. 谁判断什么

| 判断 | 归谁 | 依据 |
|---|---|---|
| 两行是不是同一个标的 | 模型 | 名称、规格、品牌、数量单位、整行原文、来源 |
| 某行是不是合计行 / 项目全称行 / 根本不是标的 | 模型（`exclude`），规则另有一条结构性兜底 | 同上 |
| 名称该用哪条的写法、价格该整组取哪条 | 模型提议，规则否决 | 同上 |
| 求和后的数量与总价是多少 | **规则重算** | 模型只指认成员，不写数字 |
| 这份报价能不能供价、能不能新增标的 | **规则** | `source_class` 与报价归属，都是结构事实 |
| 多个读法之间选哪个 | **规则** | 包金额，一个独立的数字 |
| 包金额可不可信 | **规则** | 百分号、非正数 |
| 行和与包金额对不对得上 | **规则** | 检查分级 |

模型永远不能写数字，也不能引用没给它的编号。它给的是对基线分组的**修改**，不是重画的划分。

## 2. 输入：候选与证据

每条 cob 候选带 11 个业务字段（各含 `raw_value` / `normalized_value` / `status`）、
`source{source_type,file_id,page_no}`、`source_priority`、`source_class`、`issues`，以及
**`evidence`**——这是本次新增的，因为第 8 步事后无法反查：

| 字段 | 谁盖章 | 为什么必须在抽取时盖 |
|---|---|---|
| `table_index` | 2B（HTML，`understood.table_index` 现成）、第 6 步（附件，模型回抄） | 分不清"同一张表"与"同文件不同表"，也就分不清重复行与拆行 |
| `row_text` | 2B（在 `table.rows` 里唯一命中才写，不唯一留空）、第 6 步（模型回抄整行） | 合计行、备注列、序号列这些非业务格在抽取时就丢了 |
| `quote_supplier` | 4b（文件级，模型读文件名与前 3000 字） | 一份报价属于谁，决定它能不能供价 |
| `bidder_supplier` | 第 6 步（行级，一份材料里有几家投标人时才需要） | 同上，粒度更细 |
| `winner_supplier` | 4b 判出为中标通知书时由规则填；否则第 6 步只在**上游为空时**才找 | 上游已经抽到的不重复抽 |

另有一条只读证据通道 `MergeEvidence`，在 `pipeline._merge_evidence` 里用已在作用域内的东西组装，
落盘为 `08b_merge_evidence.json`（不注册为步骤，不进 `run_state.steps`）：
文件名表、`file_class`、`quote_supplier`、`is_award_notice`、HTML 表的 role/scope/section/headers、
附件被选中页的正文前 400 字与表头、`winner_hints`、以及**每个包看到过的全部金额观测**。

第 8 步的消费者是模型，所以非结构化证据（文件名、页正文、4b 的判断依据）可以直接透传，
不必先把它结构化——这是选"定向补传递"而不是"重写统一 state"的原因。

## 3. 基线分组

规则先按**分组键相同**分组：键把值里的空白全部删掉、全角括号转半角。键只负责召回，因此比第 7 步
写进 `normalized_value` 的那个归一化值更激进——后者保留拉丁与数字之间的空格（`BeneVision TMS30A`
是内容，不是噪声），而键把它们当成同一个。这就是模型要改的基线，也是没有模型时的全部结果。
名称相等不是同一性，它只是唯一一个不需要判断就能算出来的分组。

组的编号按 `_rank` 排序后依次给出，所以基线本身与候选到达顺序无关。

## 4. 模型输出：六种 delta

每包一次调用（`merge-objects-v1`），只在"有东西可判"时发起：本包只有一条 HTML 命名候选时跳过。
输入是本包全部 cob 候选（带证据）、基线分组、包金额与其原文、包金额是否可疑、中标人名单、项目名。

| op | 含义 | 规则校验 |
|---|---|---|
| `merge` | 两个组是同一标的 | `groups` 至少两个且都在基线里 |
| `split` | 一个组其实是几个标的 | `parts` 至少两组，合起来正好等于原组成员，不重不漏 |
| `sum` | 组内若干行是同一标的的拆行 | `members` 至少两个且都在该组内；**和由规则算** |
| `exclude` | 这条不是标的 | `kind ∈ {subtotal_row, project_row, not_an_object}` |
| `name_from` | 名称取哪条的写法 | 目标必须在该组内 |
| `price_from` | 价格整组取哪条 | 目标必须在该组内，且**来源有供价资格** |

应用顺序固定为 `exclude → split → merge → sum → name_from → price_from`，与模型书写顺序无关。
组号经 `alias` 解析，所以 split/merge 之后仍能用基线组号引用。模型写 `group` 而不是 `group_id`
也接受。

**逐条否决，不整体作废。** 一条 delta 不成立只丢那一条并留痕（`reject` 写明原因），其余照常生效。
整个调用失败或两次输出都不合法时，退回基线分组，记 `repairs: merge_model_fallback`。

## 5. 报价归属（取代封闭清单）

封闭清单已删除。它要求附件候选的名称与 HTML 行**逐字相等**，否则整条丢弃，代价是整份价格清单
因一个 OCR 噪声而丢失；而它真正想挡的东西只有一类——落标人的报价。所以闸门换成来源资格：

| 条件 | 供价 | 新增标的 | 留痕 |
|---|---|---|---|
| `source_type = html` | 可以 | 可以 | — |
| `source_class = tender_requirement` | 不可以 | 不可以 | `tender_requirement` |
| 报价归属明确且**不是**中标人 | 不可以 | 不可以 | `non_winner_quote` |
| 报价归属是中标人 | 可以 | 可以 | — |
| 归属不明 | 可以 | 可以 | 交包金额裁决 |

归属取自 `evidence.bidder_supplier`，其次 `quote_supplier`；中标人名单取自本包 sub 候选里的
`is_winner`、`MergeEvidence.winner_hints`，以及被 4b 判为中标通知书的文件所写的供应商。

中标人的分项报价表就是成交明细，只是 4b 会把它归成 `bid_quote`——所以闸门不能是文件类型。
t20260202_26140146 的 7 个标的与 t20260202_26140620 的 3 个标的全部来自 `bid_quote`，
按文件类型一刀切会把这两包的清单清空。

`tender_requirement` 的行仍可补描述字段（名称、品目、规格、品牌），只是不供价、不新增标的；
名称与既有组相同就并入该组，因此不再出现在 `unmatched_summary_rows` 里。

## 6. 价格读法（readings）

一个组最终可能对应多种"读法"，每种是一个完整的四字段组（单价、数量、单位、总价），
整组取自同一来源，不逐字段拼：

- 每条**有供价资格且真的写了数字**的候选各是一种读法。空字段只从与之不矛盾的行补齐
  （`_compatible`：任一方为空则跳过，数值差 ≤0.01 视为相等）。补空的候选池比读法池大：
  只写了数量没写价格的行不能当读法，但它的数量该补还是要补。
- 模型指认了 `sum` 且通过资格门时，多一种 `sum:<group_id>` 读法，数字由规则重算。

**求和资格门**（不满足即否决并留痕，行仍算一个标的）：

| 否决原因 | 条件 |
|---|---|
| `sum_too_few_members` | 成员少于两个 |
| `sum_missing_quantity` | 有成员没写数量 |
| `sum_unit_conflict` | 成员单位不一致（都沉默可以，单边知情不行） |
| `sum_price_conflict` | 成员单价不一致——拆行的定义就是单价不变 |
| `sum_no_value` | 既没有各行总价，也没有单价 |

总价：所有成员都写了总价就取各行之和；否则用共同单价乘以数量之和。两种都由规则算。

**归一化失败的价格不是价格。** 第 7 步会把解析不出的格留成 `status=present` 而
`normalized_value=null`，所以 `{=响应报价/数量} 元` 这类模板串曾经进到 `alternatives`，
被递给第 8b 步当选项。现在读法只接受 `_number()` 能解析出数的单价或总价。

## 7. 包金额

### 7.1 来源链

严格优先级，只有一个赢家，**永远不由行和推导**：

1. 第 1 步 `package.package_amount.amount_yuan`。`raw_text` 由模型抄，数字由 `money.parse_amount`
   规则重算，模型写不了数字。
2. `package_mode = single` 且上一步为空 → `summary_amount`。
3. 仍为空 → 第 6 步从附件原文抄下的包级观测（A1）。**只有所有观测的 `raw_text` 完全相同才填**，
   记 `amount_origins = attachment`；写法不一致记 `package_amount_conflict` 且不填。
   该来源不参与对账、不触发金额检查、不做单标的补价——同一份附件既给行价又给总额会自证。

第 1 步现在还会把它看到但没选中的金额抄进 `packages[].amount_alternatives`。实测 49 个包里
22 个的金额出现在多处，此前多个竞争者被压成一个值，压的过程不可见。留痕不改判定。

### 7.2 体检

裁决者自己得先站得住。两条都是关于金额本身的结构事实，**不与标的清单比较**：

| `suspect` | 条件 |
|---|---|
| `percent` | `raw_text` 含 `%`/`％`。`parse_amount` 已经在源头拒绝，这是保险带 |
| `non_positive` | 金额 ≤ 0 |

命中即 `package_total_amount = null`、本包不对账，原文与原因写进 `amount_audit`。

曾经还有一条"金额小于本包最小行和即可疑"，已删除：一条多余标的就足以让一个正确的金额看起来
不可能，而一旦把它隔离，就失去了本该暴露那条多余标的的信号。行对不上是 `amount_overflow` 的事。

### 7.3 裁决（无死区）

只要一个组有 ≥2 种读法，包金额就有发言权。逐轮挑"能让 `|行和 − 包金额|` 严格变小、且改动最小"
的一个读法换上，直到不能再改进。每轮记 `repairs: price_bundle_by_amount`，带换前换后的偏差。

**8% 死区已删除。** 它导致 t20260401_26346106 在包金额为 1239629.63 时留下了 1241056.19：
两者相差 0.1%，唯一可用的独立数字根本没被问过。

求和读法与单行读法在同一套裁决里竞争，没有专门的求和分支。因此：

- 包金额不可用（缺失、来自附件、或体检不过）→ 不求和。标的仍是一个（模型说它们是一个标的），
  但数字保留排序最高那一行的观测值，记 `sum_unverified_no_package_amount`。
  这是一个"错但被观测到"的数量，不是编出来的数量，留痕说明是哪种。
- 包金额可用但求和读法偏差更大 → 不采纳，记 `sum_not_chosen_by_amount`。

## 8. 并列时的定序

所有"选一份来源"的地方按同一个全序取第一个，结果不随输入顺序变：

`是否 HTML 明细行` 降序 → `source_priority` 降序 → 实值字段数降序 → `file_id` 字典序 →
`page_no` 升序 → `table_index` 升序 → `candidate_id` 升序。

"是否 HTML 明细行"不再用 `source_priority >= 70` 这个阈值判定，改读第 2A 步已经给出的
`table_role ∈ {cob_detail, winner}`；拿不到表元信息时（旧数据、无证据通道的调用方）按 HTML 行原样接受。

## 9. 两条结构性排除（不经模型）

| 规则 | 条件 | 留痕 |
|---|---|---|
| 指针行 | HTML 行、自己没有任何数字价格、且 `issues` 含 `line_fields_point_to_attachment` 或某个行字段 `status = points_to_attachment`；**且**本包另有可当标的且写了价格的候选 | `html_pointer_row` |
| 项目全称行 | 名称等于项目名，或名称包含项目名且余下部分只是括号或标点；**且**公告侧另有非项目名的可当标的的行 | `项目全称行，价格并入唯一标的` / `项目全称行不作为标的` |

两条都只读状态与包含关系，不读词表、不用比例阈值。项目全称行原有的"包含度 ≥0.8"已删除：
那个比例没有依据，而一个短但真实的标的名称会被它吃掉。

项目全称行只在**公告自己确实分项列出过别的标的**时才剔除。单标的服务合同的标的名称常常就是
项目名，无条件剔除会把整个包清空。价格转移只由排序最高的那一行提供——原先按到达顺序逐行填补，
落标人的项目全称行可能先到并捐出一个投标价。

## 10. 检查分级

| `check` | 级别 | 条件 |
|---|---|---|
| `missing_cob` | hard | 包内没有标的 |
| `missing_winner` | hard | 包内没有 `is_winner = true` 的供应商 |
| `amount_overflow` | hard | 行和高于包金额超过一分钱。缺价行只会让行和更高，所以缺价不豁免 |
| `missing_line_price` | medium | 有标的既无单价也无总价 |
| `amount_underflow` | **soft** | 行和低于包金额超过一分钱 |

三处与旧版的差别，都不是调参：

- **`row_mismatch` 已删除**（随 `ROW_TOLERANCE = 0.05` 一起）。自相矛盾的行不再被降级或剔除，
  两种读法都留在 `alternatives` 里交给包金额与人工。要不要恢复、以什么判据恢复，等实测再定。
- **`amount_underflow` 一律 soft。** t20260202_26139731 包 3 的金标行和是 1579600，包金额 2431310，
  相差 −35%，而那正是正确答案：公告的标的清单本来就没覆盖整包。下溢不是缺陷，
  真正的缺陷信号是 `missing_line_price`。因此第 8b 步也不再试图"修"下溢。
- **`missing_line_price` 是新增的。** 旧版写的是 `if amount and totals:`，一行价格都没有时
  `totals` 为空、整段跳过，于是 6 个包 / 19 条无价标的静默报 success。

容差只剩一分钱（`CENT = 0.01`）：金额是逐字抄来的，推导总价按四位小数取整，低于一分是浮点与
取整噪声，不是分歧。它取代的是两个没有依据的业务容差（行内 5%、包级 8%）。

## 11. 留痕

`09_merged_projects.json` 里：

| 字段 | 内容 |
|---|---|
| `merge_decisions[]` | 每条 delta 一项：`op`、引用的组与候选、`accepted`、`reject`、模型的 `reason` 与 `confidence`；求和被否决时另记一项，带规则算不出的原因 |
| `amount_audit{包号}` | 采用的金额、原文、来源、`suspect`、是否参与对账、以及该包**看到过的全部金额观测** |
| `repairs[]` | `price_bundle_by_amount`（带换前换后偏差）、`total_from_package_amount`、`package_amount_from_attachment`、`package_amount_conflict`、`merge_model_fallback` |
| `alternatives{project_id}` | 每个有多于一种读法的组，含 `reading_kind`（`single`/`sum`）与 `sources` |
| `unmatched_summary_rows[]` | 被排除的候选与原因 |
| `list_sources{包号}` | `html` / `attachment` / `mixed` / `none`：每个标的是否有 HTML 行 |
| `provenance` | `cob_candidate_ids`、`price_candidate_ids`（读法编号）、`price_source_ids`（求和时是 `a+b`）、`sub_candidate_ids` |

`confidence` 全程只留痕，不参与任何取舍。

## 12. 没有模型时

`merge_projects(..., llm=None)` 走纯确定性基线：分组按上述键相等，排除按第 9 节两条，
资格按第 5 节，读法与裁决按第 6、7 节。`tests/test_rules.py` 全部在这一条路径上跑，
不需要服务器；它同时也是模型失败时的退回路径。
