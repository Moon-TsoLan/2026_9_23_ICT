# 全链路改造计划：上传 → 落盘 → 提取 → 入库 → 删原件

日期：2026-10-07 　状态：**设计定稿，待实施**（`tenant_id` 一项已落地）

范围：`server/`（新接口 + 工作进程）、`db/`（租户列、外键级联、覆盖式入库）、
`web/`（01 页与检索/探索的更新提示）、`prep/`（解压接入）、`src/ict`（仅路径参数化，**不动任何判定**）。

## 0. 一句话

前端批量上传 HTML + ZIP → 按同名配对并让用户确认（含"已提取过、重复会覆盖"）→
独立工作进程逐则提取 → **每则跑完立即入库**（整则替换）→ 入库成功后删原件。
检索/探索页只在检测到新数据时提示"资料库已更新 + 刷新"，**不自动刷新**。

## 3. 数据模型变更

### 3.1 `announcement.tenant_id`（✅ 已落地）

`db/001_schema.sql` 已加列 + 索引；`db/003_announcement_tenant.sql` 是给已存在库的幂等迁移。
已在 `ict_demo` / `ict_batch20261004` / `ict_report20261006` / `ict_roundkey_check` 四个库执行完毕。

### 3.2 外键改为 `ON UPDATE CASCADE`（待做，`db/004_fk_on_update_cascade.sql`）

轮次重排需要改 `project.project_id`，而三个子表的外键现在是纯 `ON DELETE CASCADE`：

| 子表 | 约束名 | 现在 |
|---|---|---|
| `cob` | `cob_project_id_fkey` | `FOREIGN KEY (project_id) REFERENCES project(project_id) ON DELETE CASCADE` |
| `bid` | `bid_project_id_fkey` | 同上 |
| `winner_coop_supplier` | `winner_coop_supplier_project_id_fkey` | 同上 |

改成 `ON DELETE CASCADE ON UPDATE CASCADE` 后，重排 `project_id` 时子表自动跟随，不需要手工改子表。

### 3.3 轮次重排算法（每次入库时对本包执行，事务内）

公告日期取自公告号前缀（`tYYYYMMDD_…` 的字典序即时间序），**不用** `announcement.created_at`（那是入库时间）。

```sql
-- ① 先把该包的所有行停到临时 id：两阶段更新，避免 PK 在交换过程中瞬时冲突
UPDATE project SET project_id = project_id || '~tmp' WHERE package_key = %s;

-- ② 按公告日期重排轮次（含刚插入的新行）
UPDATE project p SET round_no = r.rn
FROM (SELECT project_id, row_number() OVER (ORDER BY announcement_id, project_id) AS rn
        FROM project WHERE package_key = %s) r
WHERE p.project_id = r.project_id;

-- ③ 轮次映射回主键：第 1 轮不带后缀
UPDATE project SET project_id =
  CASE WHEN round_no = 1 THEN package_key ELSE package_key || '|r' || round_no END
WHERE package_key = %s;
```

新行插入时先给一个临时 id（如 `<package_key>|new`），再走上面三步；整个过程在一个事务里，失败整体回滚。
`round_no > 1` 时页面 / 星图标签显示"（第 N 轮）"。

### 3.4 覆盖式入库（整则替换）

同一 `announcement_id` 再次入库时：

```sql
DELETE FROM announcement WHERE announcement_id = %s;              -- 级联删 project → cob / bid / winner_coop_supplier
DELETE FROM supplier WHERE supplier_id NOT IN (SELECT supplier_id FROM bid);  -- 只清孤儿主体
-- 然后按正常流程重新写入（含 tenant_id）
```

`supplier` 是跨公告共享的，只能删"不再被任何 bid 引用"的行。

## 5. 状态机

任务（job）：`draft`（在建/在上传）→ `queued` → `running` → `done` / `failed`
任务项（每则公告）：`waiting` → `running`（带 `current_step`）→ `done` / `failed`

用户可见只有四种：**等待中 / 处理中 / 已完成 / 失败**。
`partial`、`review_required`、11 步明细收在开发视图（`?debug=1` 或构建开关）。

## 6. 工作进程

新增 `python -m ict.worker`（或 `ict worker` 子命令），职责是"取任务 → 提取 → 入库 → 删原件"。

- **单进程 + N 线程**（默认 `ICT_ANNOUNCEMENT_WORKERS`，2 或 4）。
  闸门（`LLM_GATE`、解析队列）本来就是进程内单例，跑在**一个进程**里才不会被放大。
  后端 uvicorn 跑几个 worker 都无所谓——队列不在它那里。
- 与后端**通过文件系统通信**：读 `jobs/<tenant>/*.json`，写 `runs/<aid>/run_state.json`。
  不引入 Redis/MQ：单机部署，状态本来就要落盘，也便于人工排查。
- **启动自愈**：把 `running` 但没有活跃任务的任务项改成 `failed`（原因：处理中断），
  避免界面上永远转圈。
- 每则的处理顺序：
  1. 解压 `<incoming>/<aid>.zip` → `attachments/<aid>/`（假包/空包只记录，不中断）；
  2. `run_announcement(aid, html_dir=<incoming>, attachments_root=<tenant attachments>)`；
  3. **入库**（含 §3.3 重排、§3.4 覆盖）；
  4. 入库成功 → 删 `<incoming>/<aid>.html`、`<incoming>/<aid>.zip`、`attachments/<aid>/`；
  5. 更新任务项状态。

## 7. 上传与配对细节

- **逐文件上传（一个文件一个请求），并发 2 路**（D17/D18），前端显示"已传 137/2008"。
  单文件上限 **512 MB**；html 限 8 MB。最小文件允许 0 字节（实测有 557 字节的
  "系统维护中"假包），只在界面标注提醒。
- 同名文件重复上传 → 跳过（返回 `skipped`），不覆盖已传内容 → 等于天然的断点续传。
- 磁盘余量 < 20 GB 或 < 15% → 拒绝上传并提示。
- 孤立 ZIP：按 D3 直接丢弃（在确认弹窗里明确写出数量与文件名）。
- 重复公告：`precheck` 返回 `already_extracted`；确认弹窗必须勾选"我确认覆盖"才能建任务。

**为什么并发是 2**：上传是纯 I/O（收字节 + 顺序写盘），几乎不占 CPU，所以并发本身不会压垮
2 核机；限制它的是**别和正在跑的提取抢磁盘**——提取侧有 4 个公告在解析、抽候选、写中间产物。
2 路在"77 GB 空闲盘 + 3.6 GB 全量数据"下足够快（全量一次约 1–2 分钟），再高收益很小。

**为什么不分片（D18）**：

| 方案 | 适用 | 我们的情况 |
|---|---|---|
| 整文件 POST + 服务端流式落盘 | 内网、单文件 < 1 GB | ✅ 主流做法；浏览器 `FormData` 本身是流式发送，337 MB 无压力 |
| 切片上传 + 服务端拼接 | 公网弱网、单文件 GB 级 | ❌ 要额外做分片管理、校验、过期清理，收益为零 |
| 对象存储直传（OSS/S3） | 有云存储、要水平扩展 | ❌ 本地部署，没有对象存储 |

落地要求：服务端**必须分块 `read` 再 `write`**，不要把整个文件读进内存；**直接写到目标路径，
不要先落系统临时目录**（4G 机器的 `/tmp` 可能很小）。

## 9. 失败与边界

| 情形 | 处置 |
|---|---|
| 上传中断 | 已传文件保留；重传跳过同名，天然续传 |
| 解压失败 / 假包 | 记录并继续，该则走 HTML-only |
| 提取失败 | 原件**保留**，任务项 `failed`，用户重新上传 |
| 入库失败 | **不删原件**（顺序保证：先入库成功再删） |
| 删原件失败 | 记日志，下一次清理时重试，不阻塞任务 |
| 服务/工作进程重启 | 启动自愈把"孤儿 running"改成 failed（§6） |
| 同一 job 内重复公告 | `precheck` 阶段已拦 |

## 10. 部署与运维

- 目标机型：**2 核 4G**（用户 2026-10-07 确认）。
- 后端：`uvicorn server.app:app`（worker 数随意，队列在工作进程里）。
- 工作进程：**1 个**（N 线程），随服务一起起：
  `PYTHONPATH=src python -m ict.worker`（装了包就能直接 `python -m ict.worker`；
  调试用 `--once` 跑一轮、`--threads 1` 串行）。
- 环境变量：`ICT_DATA_ROOT`、`ICT_ANNOUNCEMENT_WORKERS`、`ICT_SEVEN_ZIP`（7z 路径，
  现在硬编码在 `prep/extract_attachments.py:18`）、以及既有的解析/模型/DB 配置。
- 远端解析服务与隧道仍需常开（整条链路的硬依赖）。

### 10.1 2 核 4G 的容量账（结论：按用户实测值跑，够用）

| 项 | 值 | 说明 |
|---|---|---|
| 公告并发 `ICT_ANNOUNCEMENT_WORKERS` | **4** | 用户实测值。每个公告持有 HTML 文本 + 解析页 + 候选，估 100–250 MB → 峰值 0.4–1 GB |
| 解析队列 `ICT_PARSE_RUN_WORKERS` | **3** | 用户实测值；GPU 在远端，本地只等 I/O |
| 本地重活 `ICT_LOCAL_HEAVY_WORKERS` | 2 | 与核数一致（sha256、页面画像） |
| LLM 调用并发 | 8（默认） | 纯网络等待，几乎不占 CPU |
| 上传并发 | **2** | 见 §7 |
| 内存总账 | 后端 0.2 GB + 工作进程 ≤1.5 GB + 系统余量 ≈ 4 GB 内 | **不要再往上加公告并发**，4 是这台机器的上限 |
| 磁盘 | 单批原件 3.6 GB + 解压产物（峰值数 GB）+ 库 | 建议盘 ≥ 40 GB，且始终留 ≥ 20 GB |

### 10.2 解析侧并发档位（2026-10-07 实测定档）

两端各有一个旋钮，**会相乘**：

| 端 | 变量 | 含义 |
|---|---|---|
| 客户端（本地管道） | `ICT_PARSE_MAX_INFLIGHT` | ParseQueue 同时往 GPU 送几份文档 |
| 服务端（GPU 机） | `start_parse.sh --workers` | uvicorn 进程数；每个进程再有自己的 `ICT_PARSE_FILE_WORKERS` 与 `ICT_PARSE_MAX_CONCURRENCY` |

实测（同一批数据，只改这两个数）：

| N (`ICT_PARSE_MAX_INFLIGHT`) | `--workers` | batch wall | 相对基准 | batch cpu |
|---|---|---|---|---|
| 1（默认） | 2（默认） | 467.8s | 基准 | 5.3s |
| 1 | 4 | 461.0s | −1% | 5.7s |
| 1 | 8 | 478.1s | +2% | 7.4s |
| 2 | 2 | 317.3s | −32% | 8.1s |
| 2 | 4 | 298.8s | −36% | 8.7s |
| 2 | 8 | 274.9s | −41% | 8.2s |
| **3** | **4** | **276.4s** | **−41%** | 8.5s |
| 3 | 8 | 269.0s | −42% | 7.5s |

**决定：`ICT_PARSE_MAX_INFLIGHT=3` + `--workers 4`**（不加机器的前提下，3/8 只比 3/4 快 2.7%，
但服务端进程多一倍）。落地：

- 客户端：`config.py` 的默认值本就是 3，`.env.example` 现在把它显式写出来；
- 服务端：`start_parse.sh` 用 `--workers 4`，并已随本次改动**入库到 `deploy/start_parse.sh`**
  （此前只存在于服务器上，实例重建就丢）。

**行为要点**

- **删原件只在入库成功之后**；提取失败（`report.status == "failed"`）或入库失败，原件与解压产物都留着，任务项记 `failed` 与错误原因，用户重新上传。
- 提取返回 `partial` 照常入库（按 D6/D7，`partial` 只是开发期视图）。
- 两个锁：任务元数据写文件串行（同批多线程共享一份 job 字典）；**入库串行**（轮次重排要读库内现状，并发会撞唯一键）。
- 启动自愈：上次进程被杀留下的 `running` 项 → `failed`（原因"处理中断（工作进程重启）"）。
- `worker` 用锁文件 `<DATA_ROOT>/jobs/default/.worker.lock` 防止多开；崩溃残留的锁要手动删或加 `--force`。
