# 候选包组行与合并 delta 语义

日期：2026-10-09。适用实现：`src/ict/steps/s08_merge.py`，提示词 `merge-objects-v3`。

本文固定后续讨论所用的术语，并记录当前代码实际怎样执行。它不修改规则、不授权任何流程改造。
已实现的行为写在第 1—7 节；案例证据写在第 8 节；尚未确定的设计问题写在第 9 节。
第 9 节不是实现规范，也不是新增待办清单。待办的唯一出口仍为 `eval/待优化清单.md`。

最高约束仍是 `../AGENTS.md`。主流程契约见 `主路线多步Agent设计契约.md`，
第 8 步总体规范见 `第8步标的合并规范.md`。本文补充这些文档中容易混淆的术语和操作边界。
涉及执行细节时，下面列出的函数是本次核对的直接依据。

## 1 先区分三种不同的判断

判断两个候选描述同一个标的，并没有回答它们的数量应当怎样处理。
一份报价表与公告各写同一批设备，可以描述同一个标的，但数量只能计一次；
一份点位清单按安装位置分别列出同型号设备，也可以描述同一个标的，但各位置的采购数量可能需要累加。
同一项服务的整体描述与组成点位描述之间，则还存在整体与组成部分的关系。

后续讨论分别使用以下三个说法，不能用笼统的“合并”替代：

| 判断 | 要回答的问题 | 当前主要操作 |
|---|---|---|
| 标的同一性 | 哪些候选最终属于同一条 COB | 基线分组、`merge`、`split`、`exclude` |
| 观测关系 | 同组候选是重复记载、独立可累加明细，还是其他读法 | 当前只有 `sum` 明确表达累加，其余主要落入备选价格读法 |
| 字段归属 | 某条候选的某个属性是否描述目标 COB | 组内补空、`fields_from`、排除行的自动捐赠 |

观测关系并不是当前 schema 中已经存在的独立字段。这里命名这个概念，是为了说明现实现缺少什么，
不能因此认为程序已经保存了“重复记载”“独立明细”“整体与组成部分”的结构化判定。

## 2 包 组 候选行 原文行和最终 COB

| 名称 | 本文固定含义 | 不应推导出的含义 |
|---|---|---|
| 公告 | 一次主流程处理的公告及其附件上下文 | 不能凭同一项目编号把别则公告的附件搬进来 |
| 包 | 公告明确的采购包；最终输出一个 `Project`，其中包含 `cobs` 和 `subs` | 不是候选组，也不是一个标的 |
| 原文行 | HTML 表、文档表或文本中的一处原始记载 | 不保证一行恰好对应一个实体；一行可能包含多个值、汇总或说明 |
| 候选行 | 一个 `Candidate` 对象，是模型输出并经封装的一次实体字段观测 | 不保证与原文行一一对应；不是已经确认的真实标的 |
| 基线组 | 本包 COB 候选按名称分组键相同得到的临时容器 | 不证明成员同一、不证明重复，也不证明可相加 |
| 当前组 | 应用 `exclude`、`split`、`merge` 后仍存在的 `Group` | 不是原文中的一张表或某个文件，也没有独立的业务主键 |
| 最终 COB | 一个保留下来的组经字段协调和价格选择后生成的标的对象 | 不等于某条完整原文行，也不保证所有属性来自同一个候选 |
| SUB | 投标供应商候选及其最终供应商对象 | 不参加本文件所述八种 COB delta；当前走 `_merge_entity()` |

包先由上游确定。第 8 步按候选的 `project_id` 分配到已知包；无法分配的进入
`unassigned_candidates`。八种 delta 都只作用于当前包，不能新增包、改变候选包归属或跨包合并。

第 8 步的 `project_id` 使用提取阶段的项目名称与包号。数据库入库阶段的项目键另有项目编号、包号和轮次逻辑，
不能用数据库主键解释模型看到的临时组号。

## 3 编号和字段观测

`candidate_id` 标识本次运行中的一个候选。它由抽取阶段按序发号，不是跨运行稳定的原文行主键。
`group_id` 标识当前包内的临时分组，不同包可以有相同组号；它不是最终数据库的 `cob_id`。
`file_id` 是附件索引中的文件标识，单独一个文件标识不能定位它的某张表、某行或某格。

字段由 `FieldObservation` 承载：

| 字段 | 含义 |
|---|---|
| `raw_value` | 候选抽取时留下的值，保留原始写法；不等于已经对照原件证明无误的值 |
| `normalized_value` | 规范化或后续补值得到的业务值 |
| `status` | `present`、`missing`、`points_to_attachment`、`unparsable`、`conflict` 等状态 |
| `normalization` | 换算、目录匹配或补值等过程信息 |

当前 `_value()` 优先取非空 `normalized_value`；它为空时，只有 `status=present` 才回退到 `raw_value`。
因此，仅把 `normalized_value` 设为空，不能表达“这格被否定”：`present` 状态会重新读出原值。
已有规范值的字段被标成 `conflict` 后，也仍可能把那个规范值输出，冲突并不自动清空它。

每条候选的 `source` 包含格式、文件与页号；`evidence` 可包含表序号、行文本、列单位和供应商归属。
这些字段有助于追踪记载，但目前没有覆盖所有候选的稳定原文行编号、单元格坐标或明细业务编号。

## 4 基线分组与一组一条 COB

依据：`_baseline()`、`_norm_name()`、`merge_projects()`、`_reconcile()`、`_to_cob()`。

1. 只在本包内处理 COB 候选。
2. 名称分组键去空白、转换全角括号，键相同者进入同一个基线组；规格、品牌、单位都不参与基线键。
3. 模型通过 delta 修改分组；没有 `split` 时，单位冲突本身不会把组拆开。
4. 一个保留下来的、具有可输出名称的组最终生成一条 COB。全部成员都无独立标的资格的组不会生成 COB。
5. 没有 `sum` 时，程序不会把组内数量自动相加，也不会自动按单位分别求和。

描述字段按 `_rank()` 排序补空，两个非空属性不一致时记录冲突。普通价格读法只从有供价资格的成员建立，
将单价、数量、单位、总价作为四字段价格组处理。一组可以拥有多种价格读法，最终只输出其中一种。
整组没有价格读法时，另有保留已观测数量和单位的路径。

候选数量不等于最终 COB 数量。十个候选都留在同一个组中，可以最终只有一条 COB，
而那条 COB 的数量可能只取自其中一个候选。这正是终端管理器案例发生的过程。

## 5 八种 delta 的实际语义

以下“来源候选”指 delta 的 `candidate_id`。“接收组”指 delta 的 `group_id`。
特别是 `fields_from`，`candidate_id` 是字段供给方，不是接收方。

| 操作及主要参数 | 当前实际作用 | 不会自动做到的事 |
|---|---|---|
| `merge(groups)` | 把至少两个可解析的组的成员并入一个新组，表达它们属于一个标的 | 不自动累加数量，不证明成员是重复观测，也不自动选定每个字段来源 |
| `split(group_id, parts)` | 将一个组的当前成员划分成至少两个非空子组；应用校验要求正好覆盖原组成员 | 不复制候选，不把一条候选拆成两个，不按单位自动求和 |
| `sum(group_id, members)` | 为当前组登记一份候选子集，程序据此建立一条求和价格读法 | 不新增 COB，不拆组；不保证这份读法最后被选中 |
| `exclude(candidate_id, kind)` | 将候选移出其当前组；该组为空时移除组 | 不等于彻底禁止这条候选再提供字段；当前仍有自动捐赠 |
| `name_from(group_id, candidate_id)` | 选择当前组内某个成员的名称作为输出名称 | 不移动候选、不改变其包归属，不选择其他描述属性 |
| `price_from(group_id, candidate_id, keys?)` | 从当前组内有供价资格的成员选择价格读法；可只取四字段的指定子集 | 不是求和操作；没有 `keys` 时不能指向不含数值价格的行 |
| `fields_from(group_id, candidate_id, keys)` | 将本包某候选的指定非金额字段提供给接收组，只补空；来源可在其他组或已被排除 | 不把来源候选移动到接收组，不自动累加，不覆盖已写的描述值 |
| `category_from_announcement(group_id, raw_item)` | 指定公告概要品目条目；去空白校验输入项后回到原文，查目录并补空 | 模型不自写编码、名称；不覆盖已有品目，也不能自行新增公告概要条目 |

### 5.1 求和与价格读法

`sum.members` 是当前组成员的子集，不要求覆盖整个组。程序会滤掉不在当前组的成员，
若剩下不足两个则拒绝。程序当前没有表达“这个子集是一批、另一个子集是另一批”的完整分批关系。

`_sum_bundle()` 要求每个成员有可解析数量；已写出的单位不能有两个不同字符串，
已写出的单价不能有两个不同数值。单位部分缺失不会直接导致拒绝，全部缺失时求和单位为空。
所有成员都有总价时加总总价，否则有单价时用单价乘数量；两种方式均无法算出值时拒绝。
当前没有单位语义等价声明，也没有单位换算表达。

求和成功会建立 `sum:<group_id>` 读法。普通单行读法仍然存在，求和读法并不会立即替换输出。
当前 `_arbitrate()` 用可信的、非附件补入的包金额比较读法，严格缩小行和与包金额差距时才换。
包金额缺失、可疑或仅由附件补入时，不用它确认这条求和读法。
第 8b 步也只是从已有读法中选择，并不重新生成分组或新增求和成员。

因此，必须区分：模型提出求和、求和登记成功、算术校验通过、求和读法被选为最终输出。
`accepted=true` 不能单独证明最后输出的是求和结果。

### 5.2 字段选择和算术校验的边界

`fields_from.keys` 允许品目名、品目码、类别、品牌、产品供应商、规格型号、数量和单位，
不允许单价和总价。数量、单位虽不是金额，却仍是价格组中的成员，补入时有单独路径。
一次字段补空不等于模型确认了可相加关系，也不等于程序证明该字段描述目标标的。

`price_from` 不带 `keys` 时选择整份价格读法；带 `keys` 时按指定字段取值，其余字段保留已有值。
当前实现没有通过这个操作重新计算跨来源组合后的总价。
后续金额对账还可能改变所选读法，必须连同 `repairs` 和最终溯源一起检查。

当前普通读法和 `price_from` 有供价资格检查；`sum` 的成员校验与算术函数没有再次逐个调用
`_ownership()`。不能把“有结构与数值校验”表述为“程序已经证明了所有求和成员的业务归属”。
本文记录该实现边界，不在此改动逻辑。

## 6 执行顺序 组号引用和排除后的字段捐赠

模型先对基线组输出一批 delta，代码按以下固定顺序应用，与 JSON 中书写先后无关：

```text
exclude → split → merge → sum → name_from → price_from → fields_from → category_from_announcement
```

`_validate_merge()` 先检查整份回答的基本形状、输入编号和操作范围，失败时带错误重试一次；
两次仍不合法或调用失败时退回空 delta。基本校验通过后，应用阶段再逐条记录接受或拒绝。
因此，“逐条拒绝”指应用阶段，不能理解为任何非法编号都只影响单条操作。

### 6.1 split 后的引用限制

`split` 的新组号由代码分配。模型本次输入没有这些新组号，基本校验只允许输入里的基线组号。
当前 `alias` 将旧组号指向第一个新组，没有为第二个及后续新组提供可供本次回答使用的独立引用。
`merge` 后原组号可以通过别名指向合并出的新组。

这意味着，当前协议不能直接完整表达“先把一个组按单位拆成两组，再对两组分别求和”。
不能仅在提示词里要求输出两个子组的 `sum`，就声称实现已能执行；
需要先讨论怎样引用拆分后的每个子组。

### 6.2 当前两条自动捐赠路径

第一条在 `_apply_deltas()` 内：某候选被排除时，如果原组还有其他成员，
它已写出的非金额字段会登记为原组的补空来源。该登记没有逐字段询问模型。
后续 `split`、`merge` 会新建 `Group`，当前代码并不自动继承原组的 donor 登记。

第二条在 `_donate_excluded()` 内：所有 delta 应用后，如果只剩一个非空活组，
被排除候选的非金额字段会登记给这个组，包含规格、数量和单位。
`kind=project_row` 还可登记价格组字段，金额仍受供价资格约束。
这里计数的是独立标的资格过滤之前的活组，不是已经生成的最终 COB。

第二条并不要求来源候选与接收组原来同组，也不要求 `kind=project_row` 才能捐赠规格和数量。
它实际把“只剩一个活组”当成跨组补字段的依据。这不能证明点位属性就是整体属性。

### 6.3 明确指定字段归属是什么意思

“明确指定”是讨论中的改进方向，不是当前已经取消自动捐赠。
它要求模型说明“哪条候选的哪个字段，可以补给哪个组”，而不只说明“这条候选不是独立标的”。

例如，在主链路案例的包 1 中：

```json
{"op":"fields_from","group_id":0,"candidate_id":"cand_000010","keys":["spec_model"],"reason":"……","confidence":0.8}
```

这句话准确表达的是“把点位候选 cand_000010 的规格补给组 0”，不是把 cand_000010 合入组 0。
对本案例，这个决定应当被认为缺乏正确的字段归属依据：候选的 1G 描述具体点位，不能直接代表整体服务。
示例只解释参数方向，**不是建议输出这条 delta**。

如果被排除候选确实写着适用于目标标的的统一品牌或品目，模型可以点名那些字段；
如果没有能够证明适用关系的证据，就没有依据发出这个补值操作。
采用这种方式还需要讨论两条自动捐赠路径各自保留什么，不能只改提示词假装自动行为已消失。

## 7 来源证据能说明什么

同一文件、不同文件、同一张表、不同表都不是重复或累加的充分条件。

| 记载位置 | 可能关系 | 还需要什么证据 |
|---|---|---|
| 同一表的两行 | 不同位置独立采购；重复录入；小计与明细 | 行序、业务序号、位置或分项上下文、汇总关系 |
| 同文件不同表 | 按区域分别列项；汇总与展开；同一批次重复列示 | 表标题、章节、覆盖范围、明细编号及交叉指向 |
| HTML 与附件 | 公告概要与完整明细；重复的成交清单；采购需求与成交报价 | 文档角色、成交归属、明细覆盖范围、对应关系 |
| 不同附件 | 同一清单的副本；不同采购部分；不同投标人的报价 | 文件角色、报价主体、清单覆盖范围及稳定的明细锚点 |

当前第 8 步真正发送给模型的是 `_ask_merge()` 构造的 payload，不是整个运行状态。
候选视图包含业务字段、字段状态以及可获得的来源、表角色、章节、报价归属和行文本。
`08b_merge_evidence.json` 中有数据，不等于每一个字段都已进入合并调用；
当前候选视图没有逐项展开其中的 `attachment_pages` 文本摘要和表头。

HTML 的 `_row_text()` 按候选名称寻找原表行，只有唯一匹配时才保留行文本，且最多 400 字。
同名多行恰好是需要判断累加关系的情况，但它会导致行文本缺失。
终端管理器案例十条候选的 `row_text` 均为空，只有相同表号和已抽字段，不能把这种输入称为完整原文证据。

`digest` 解决文件字节重复；它不能证明不同字节的文档记载的是不同采购数量，也不能证明两个相同型号的行重复。
普通价格读法对相同四字段组合去重，只是在去掉重复的备选读法，并没有证明候选是同一次采购事实。

提示词可以让模型区分这些概念，但不能补造已经没有传递下来的业务上下文。
若两个不同业务世界投影成完全相同的候选输入，一个世界应计一次、另一个世界应累加，
任何模型都无法只凭这些输入可靠区分。能输出 JSON 与能确定业务事实是两件事。

## 8 三个案例的实测解释

依据为本地 `online-runs/` 下载产物，本次只读核对，没有调用模型或 OCR。

### 8.1 t20260212_26175071 终端管理器

`cand_000012` 至 `cand_000021` 都是同名、同品牌、同型号、单价 2000 的 HTML 候选，位于基线组 2。
十条数量合计中，单位“个”的三条为 2、1、3，共 6个；单位“台”的七条共 10台。
如果确认这些行是不同采购明细，按原文单位分别汇总应是 6个、12000元与 10台、20000元。
如果进一步确认本组两种单位均表示同一种设备计数，合计为 16，金额为 32000元；
最终显示哪个单位仍需要明确的处理语义，不能把“16件”当作原文明确写出的计价单位。

实际没有 `split` 或针对组 2 的 `sum`。提示词禁止单位不一致时求和，代码也会拒绝混合单位求和。
因此，十个成员仍然只生成一条 COB，并从单行价格读法中选择。
`repairs` 记录对账将 cand_000012 的 2个、4000元换成 cand_000017 的 3个、6000元；
差距从 2004218.6 缩小到 2002218.6。这里减少的是包金额差距，没有完成明细汇总。

P10红色屏模块的五条成员则获得 `sum`，形成 1728块、293760元的读法，并被对账选中。
这种不同结果来自操作和单位约束，不是模型直接写出了一个正确总数与一个错误总数。

### 8.2 t20260202_26141964 主链路与备用链路

## 9 后续设计讨论的边界

以下是待讨论问题，不是本次新增的规则或承诺实现的方案：

1. 标的输出粒度与计量粒度。能否让同一标的保留多个计量子组，或允许同名不同单位的两条 COB？
   需要定义它们是业务上不同标的，还是同一标的的保守分开计量，避免拿 `split` 的“不同标的”含义代替后者。
2. 拆组后的独立引用。若采用两个 COB，必须能在同次模型回答中分别引用两个新组，再分别累计；
   当前只把旧组号指向第一子组的语义不足以表达。
3. 组内单位含义声明。模型是否可以在点名成员范围内声明计数含义等同，并选择一条来源的单位写法？
   不应由此推出全局“个＝台”，也不应暗中扩展为包装换算。
4. 重复观测、独立明细与整体组成关系。需要明确模型看到哪些业务锚点；证据不足时如何保留未决关系，
   而不是因为单位一致、名称一致或金额更接近就把事实视为已证实。
5. 字段归属。排除行自动给原组、给唯一活组的两条路径要分别讨论；显式 `fields_from` 可表达搬运方向，
   但模型判断可靠性仍依赖来源上下文，不能保证补值必然正确。
6. 决策与算术分工。模型决定关系、成员与字段来源，程序计算数值；结构校验通过不等于业务关系真实。
7. 未决结果的表达。当前 `partial`、`conflicts`、`alternatives` 并未完整承载所有重复或累加关系的不确定性；
   是否需要补充表达，要先定语义再讨论代码，不能默认现有字段已经覆盖。

整体提示词优化、品目规范化补充与这些协议问题需要分别验收。提示词改善输入理解，
协议决定模型能够表达哪些决定，代码决定这些决定如何落地，证据决定哪些事实有可能被判清。
