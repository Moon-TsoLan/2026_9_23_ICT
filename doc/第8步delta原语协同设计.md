# 第 8 步 delta 原语协同设计

日期：2026-10-09。状态：**设计稿，未实施，待讨论后另行批准实施**。

本文按用户要求设计第 8 步的候选合并协议。用户本次批准的是新增本文，不是修改代码、提示词或既有规则。
当前实际行为仍以 `候选包组行与合并delta语义.md` 和代码为准；本文中的“应当”“禁止”“新增”均指拟议协议。
本文不取代现行契约，不另设待办清单。待办唯一出口仍是 `../eval/待优化清单.md`。
若方案获准实施，应同时修订现行第 8 步规范、主路线契约和实现细则，明确新旧路径，避免保留两套生效语义。

## 1 结论与改造边界

建议保留现有八种 delta 的主要职责，增加一种字段否定原语 `fields_reject`，并补齐三项协同机制：

1. **组与计算结果可以显式命名和引用。** `split` 的每个子组都能被后续操作点名；`sum` 产生独立读法，
   `price_from` 明确选择该读法。旧组被消耗后失效，不再偷偷指向第一个子组。
2. **成员关系、计量关系、字段来源分别表达。** `merge/split/exclude` 管输出粒度，`sum` 管可累加观测，
   `name_from/fields_from/price_from` 管最终取值，`fields_reject` 管误填字段。排除候选不自动授予其字段归属。
3. **最终结果需要完整交代计量观测。** 未计入的数量或总价观测须说明是重复、冲突备选还是未决，
   不能默认十行同名货物只取其中一行。已明确选择的来源不再被包金额对账暗中替换。

内容判断仍交模型；程序负责引用、集合、资格、依赖和算术的校验执行，不增加服务关键词、单位同义词或文件筛选规则。
同一文件、不同文件、同表、跨表只是证据，均不自动决定重复或累加。

改造范围为第 8 步的模型输入、输出协议、执行器和审计。第 1—7 步、附件读取、OCR、SUB 合并、数据库及页面结构不改。
为了覆盖单标的服务的误填规格，第 8 步还必须调整“单条 HTML 候选跳过模型”的调用条件。
“只改最后一步”指上述处理边界，不代表只改一份提示词或不涉及执行语义变化。

## 2 当前问题为什么不是增加一种 delta 就能解决

| 当前行为 | 协同缺口 | 本设计对应处理 |
|---|---|---|
| `split` 生成子组，但旧组号只别名到第一个子组 | 一次回答无法分别给两个子组配置求和和取值 | 命名子组，显式引用，消耗旧组 |
| 一个组只有一个 `sum_members` | 重复配置会覆盖，计算结果也不能独立引用 | 命名计算读法，多个结果互不覆盖 |
| `sum` 增加备选价格读法 | 求和合法不等于最终采用，可能仍输出单行数量 | 用 `price_from` 绑定求和结果 |
| 不求和便从单行读法里选 | 未计入的独立明细可以无声消失 | 计量观测交代与未决检查 |
| `exclude` 后给原组或唯一活组自动补字段 | 排除点位也可能把带宽、数量捐给整项服务 | 只保留证据，显式补给指定组和字段 |
| `fields_from` 只补空 | 已有错误值不能被明确否定或选择其他来源 | 字段否定与显式选择 |
| 金额对账可改选价格读法 | 模型作出的明细决定不是最终决定 | 对账报告差异，保护已绑定结果 |
| 单条 HTML 候选通常不调用模型 | 服务范围误填规格根本进不了最后一步判断 | 有 COB 的包也进行字段归属检查 |

这不是推翻现有原语。现有操作已经覆盖大部分业务动作，主要缺少可组合的引用、明确的最终取值和未选观测的处理语义。

## 3 四种对象与引用

### 3.1 不可变候选、活组、读法、字段绑定

| 对象 | 含义 | 是否直接输出一条 COB |
|---|---|---|
| 候选观测 `Candidate` | 上游抽取的字段及来源，原始内容不因 delta 被修改 | 否 |
| 活组 `Group` | 当前准备形成一条 COB 的成员集合 | 是，但仍须通过既有新增标的资格检查 |
| 计量读法 `Reading` | 一个候选或一棵求和表达式的数量、单位、单价、总价 | 否 |
| 字段绑定 `Binding` | 某最终组的某字段采用哪个观测、读法或明确空值 | 否 |

一个活组表示一个**输出单元**。模型可以因为单位或计价粒度不同，把同名同型号候选分成两个输出单元；
这不强行宣称它们是两种不同实物。最终 COB 可以同名，分别显示 10台与6个。
不在本次设计中引入全局“个＝台”，也不把“批”“根”转换为同一种单位。

### 3.2 引用约定

所有引用仅在当前包、本次合并调用内有效：

| 引用例子 | 来源 |
|---|---|
| `c:cand_000012` | 输入中已有的候选编号 |
| `g:2` | 输入中已有的基线组号 2 |
| `g:terminal_ge` | 本次 `split/merge` 的 `as` 显式声明的新组 |
| `r:terminal_ge_sum` | 本次 `sum` 的 `as` 显式声明的新计算读法 |
| `p:amount` | 输入中已存在的本包金额及其来源状态，仅供显式整体金额绑定 |

上述前缀用于区分类型，不改变上游候选编号，也不是数据库主键。
模型可以声明新的结果编号，不能杜撰候选、包金额或尚未声明的组、读法。
结果编号必须唯一，不能重用已消耗的组号。不同包中的相同临时编号互不相干。

## 4 九种原语的固定语义

每条 delta 带 `id`、`op`、`reason`。下表列出其余参数；完整字段语义若实施，仍统一注册到 `fields.py`，
不在提示词中另外维护一套枚举定义。本文是协议设计说明。

| 原语 | 主要参数 | 固定效果 |
|---|---|---|
| `exclude` | `candidate_ids`、`kind` | 从活组成员中移除候选；原始证据和可引用观测保留；不自动搬运任何字段 |
| `split` | `group_id`、`parts:[{as,members}]` | 用命名子组完整分割当前组，旧组失效 |
| `merge` | `group_ids`、`as` | 把若干活组并成一个命名组，输入组失效；不隐含数量累加 |
| `sum` | `group_id`、`sources`、`as` | 声明本最终组的可累加计量读法；程序计算，结果不自动绑定 |
| `name_from` | `group_id`、`candidate_id` | 最终名称采用本组成员的名称观测，不改变成员 |
| `price_from` | `group_id`、`source`、可选 `keys` | 将候选、求和读法或允许的包金额字段绑定到最终组 |
| `fields_from` | `group_id`、`candidate_id`、`keys`、`mode` | 将指定非计量字段补给或选给指定最终组，允许跨组或来自已排除候选 |
| `category_from_announcement` | `group_id`、`raw_item` | 保留现有公告概要品目查目录、只补空、不覆盖语义 |
| `fields_reject` | `target`、`keys` | 否定某候选的字段可用性，或明确令某最终组字段为空；原始值留存 |

### 4.1 拓扑操作：exclude、split、merge

- `split.parts` 必须无重叠地覆盖操作时的全部组成员；每个子组非空。不能漏行、复制行或引用别组行。
- `merge` 只能消费当前仍存活的组。新组完整继承其成员，不继承先前编号的隐含别名。
- 同一候选在拓扑上最多属于一个活组；排除候选不属于任何活组。
- 拓扑操作按模型给出的先后顺序执行，允许 `merge→split→merge`。不再按操作种类整体排序。
- `sum`、取值和字段否定引用最终组；拓扑完成后不再消费这些组。若需要再拆组，应先写完拓扑再配置取值。
- 被排除候选仍可被 `fields_from/price_from` 点名，但这是一条独立的字段归属决定。
  `exclude(kind=project_row)` 本身不授权把金额或任何描述字段捐给详细标的。

例如 HTML 项目全称行被排除，而附件抽出三条详细标的：模型可以分别给三组补共有品目；
不能仅凭“只剩这些组”传播品牌、规格或项目总金额。每次传播都必须指明来源、目标和字段。

### 4.2 sum：表达可累加关系，不代替最终选用

`sources` 可引用候选读法或此前声明的求和结果。嵌套求和只为组合已有明细，不引入乘法、均价、折扣或单位换算。
同一组可以有多个命名读法，例如附件甲汇总与附件乙汇总，交由最终绑定选择。

程序展开到候选叶子后执行以下检查：

1. 叶子来自本组成员，或本包已排除且被模型明确用作本组计量来源的候选；不能把另一活组的整笔采购数量搬走。
2. 每个叶子都满足既有供价资格；需求文件或明确非中标人的报价不能因包在 `sum` 中而绕过限制。
3. 一个求和表达式内不能重复使用同一候选叶子，包括经两个中间结果间接重复的情况。
4. 每个叶子都有可用数量；单位和单价兼容性、金额计算与精度沿用现有 `_sum_bundle` 语义。
   当前语义是非空单位不冲突、非空单价不冲突；缺失值仍须如实留痕，不能宣称单位已经被证明相同。
5. 全部叶子有总价时累加总价；否则有兼容单价时按数量计算；现有算术条件不成立就拒绝该读法。

同值不等于同一叶子。两行都写396块，若模型认定它们是不同采购明细，可以都计入。
同一候选经不同表达式再次进入同一求和，则是结构性重复计数，应拒绝。

`sum` 成功只表示读法算得出来。必须再用 `price_from` 引用它，才能成为该组的最终计量结果。
不能继续靠包金额接近程度决定是否采用。

### 4.3 price_from：确定最终计量字段

`keys` 可选 `unit_price/quantity/unit/total_price`，省略时取该读法可提供的字段。
绑定以有效的标准化数值为基础，不从 `unparsable` 等状态恢复不可用原文。
来源无对应有效值时拒绝绑定，不能静默换一行或换一套读法。

绑定最终结果时还需遵守：

- 同组同字段不能有两条相互竞争的显式来源；重复的同来源操作可以幂等，来源不同则报冲突，禁止“最后一条赢”。
- 数量与单位作为计量对处理。更新数量时携带其来源单位；不能留下另一种单位的旧值。
- 混合来源补字段时，模型须说明它们属于同一计价范围，相关数量观测的关系须在第 5 节交代。
  程序能检查已知数值是否冲突，不能替模型证明两份文件属于同一批采购。
- 重新计算 `单价×数量` 只在已选择的来源关系允许时发生。已有总价与乘积不一致时保留来源差异和检查，
  不为了对账改写原文总价，不增加新的容差。
- 一个候选叶子的整笔数量或总价不能进入两个不同最终组的成品。共享单价和描述字段可以被显式授权，
  共享一笔采购数量不能被当作两笔采购。
- `p:amount` 只能提供 `total_price`。只有模型明确判定本包唯一最终 COB 覆盖整个采购包、且金额通过既有可用性检查时才可绑定。
  不能据此推出数量、单价，也不能给多个 COB 平均或重复分配包金额。附件来源金额的既有限制保持。

模型路径中撤掉“唯一 COB 自动取包金额作标的总价”的隐式赋值，改为上述显式绑定。
数量、单价或总价缺失时仍可保留其他合法字段；不为了拼出四字段齐全的读法制造数值。

### 4.4 fields_from：方向、字段和覆盖方式都明确

本设计将 `fields_from` 限于品目三字段、品牌、制造商、规格型号等非计量描述字段。
当前能通过它搬运的 `quantity/unit` 改由 `price_from` 统一处理，避免两个原语各自修改计量范围。

- `mode=fill`：只补目标空缺；非空且不同则不覆盖，留下冲突。
- `mode=select`：明确选择该候选的观测作为最终值，可解决目标已有非空值的争议。
- 不指定 `keys` 不合法；不能把整条候选当作“信息包”自动灌入目标。
- 来源字段必须存在且未被否定；显式目标组否定优先于补值，不能靠 `fill` 复活。
- 同字段的多条竞争性 `select` 应拒绝。默认组内协调不得覆盖显式选择。
- 多条 `fill` 向同一空格提供不同值时应报冲突，由 `select` 明确选择；不能靠回答顺序先到先得。
- 品目名称和编码按同一次来源决定协调；显式选择造成目录不一致时应报告冲突，不能静默混搭两套品目。

`name_from` 保留为名称的专用选择操作，仅采用最终组成员的名称。
`category_from_announcement` 保留专用查表行为；它与其他显式品目选择冲突时报告冲突，不依赖执行顺序碰运气。

### 4.5 fields_reject：否定字段，保留原始观测

新增这一原语是必要的。现有 `exclude` 只能否定整行，现有 `fields_from` 无法表达“这项服务仍成立，但这一格不属于规格”。

`target` 支持两种范围：

| 范围 | 含义 | 例子 |
|---|---|---|
| 候选 `c:...` | 这条观测中的指定字段不具备该字段语义，不能供给任何组或表达式 | 服务范围被抄入规格；点位带宽被抄入整项服务规格 |
| 最终组 `g:...` | 明确决定该最终 COB 的指定字段为空；其他来源也不再自动补入 | 当前所有“规格”都属于服务说明，本项没有可确认规格 |

候选级否定在读法计算前生效，组级否定在输出时具有最高优先级。
数量被否定时，其所属原始读法不能继续拿该数量派生总价；明示原文总价是否可单独使用须另行绑定。
对象名称不支持字段否定：不用此操作生成无名 COB，应通过 `name_from` 选合法名称或通过 `exclude` 处理整行。

否定只是第 8 步的有效性视图。原始候选、`raw_value`、`normalized_value`、字段状态不就地改写，
以便复核“当时抄到了什么、模型为何否定”。不能只写 `normalized_value=null`，再让 `_value()` 从原文恢复该字段。

“服务通常没有规格”作为模型判断背景，不改成“品目为 C 就清空规格”的规则。
明确标识服务交付类型的有效规格仍可保留；服务范围、要求、时间、标准不应打包代替规格。

## 5 计量观测交代：不选的行去了哪里

仅有 `sum` 与 `price_from` 仍不足以区分“选一行是因为其他行重复”还是“漏掉了其他独立明细”。
因此增加回答元数据 `quantity_accounting`，不再新增一种业务 delta。

### 5.1 四种去向

| 去向 | 声明方式 | 含义 |
|---|---|---|
| 已计入 | 由最终选中的候选或求和结果自动展开叶子 | 这笔数量/总价进入最终结果 |
| 重复记载 | `relation=duplicate`，给出 `of` | 与一个已选候选或已选汇总表示同一计量范围，不再计一次 |
| 冲突备选 | `relation=alternative`，给出 `of` | 对同一计量范围有不同观测，选择来源，但冲突保留 |
| 未决 | `relation=unresolved` | 证据不足，不能确认该计入、重复还是冲突备选 |

`quantity_accounting` 每项包含 `group_id`、`observation`、`relation`、必要时的 `of`、`reason`。
只需列出未计入的有效计量观测；已选读法的叶子由程序展开，不要求模型重复列一份成员清单。
只有数量或整笔总价实际被绑定到成品时，相关叶子才算已计入；只共享单价或单位不算消费这笔采购数量。
`observation` 可为候选或已声明读法，但程序最终要覆盖到全部相关候选叶子。

最终组中所有具有可用数量或总价的成员都必须得到去向；不供价的需求观测不强求计入，仍保留其资格原因。
被 `exclude` 移出组的候选不再强制属于某个最终组，但其排除决定必须留痕；若再次用作计量来源则进入相应组的检查。
单行且没有其他有效计量观测时，默认采用该行可自动完成交代。
不能把多个有效观测无声明地都降为默认备选读法。

### 5.2 谁判断，谁校验

模型判断观测是否表示相同采购范围，以及未计入的原因；程序检查引用、覆盖和数值自洽。
`duplicate` 必须指向最终采用的读法或其叶子，不允许形成循环、自我解释或指向未选备选读法。
已知单位、数量或同范围总价互相矛盾时，不能用“完全重复”掩盖，应声明 `alternative` 或 `unresolved`。
缺失信息不能被结构校验当成已经证明相同。数值相同也不能自动生成 `duplicate`。

例如 HTML 写总数16，附件写明细2、5、9：可选附件求和，再声明 HTML 观测重复于这个求和结果。
附件甲覆盖点位1、2，附件乙覆盖点位2、3：选甲1、甲2、乙3累加，声明乙2重复于甲2。
模型必须依据点位锚点作出判断；“不同文件所以都相加”不成立。

### 5.3 仍有未决时怎样输出

若一个组还有未交代或未决的计量观测，不能把所选子集的数量/总价包装成完整汇总。
建议该组 `quantity/total_price` 留空，保留有依据的名称、描述、单价和单位；
子集的已知数值存入审计，不放入公开数量冒充总数。
若单位本身也存在未决冲突，单位同样留空。

在现有 `conflicts` 中记录 `kind=unresolved_observation_relation`，并使合并结果为 `partial`。
不能只依赖当前“缺少单价和总价”的检查，因为单价2000、数量漏计的错误可能通过那个检查。
已明确选择冲突备选时可以输出所选值，同时保留备选和选择理由，不能伪装为无冲突数据。

这是保守输出策略的明确改动，需与协议一起批准实施；它不等于要求模型必须求和。
模型完全可以判断十条是重复记载，但必须作出可审计的判断。

## 6 执行顺序与失败语义

### 6.1 一次包级回答，分阶段执行

建议内部协议版本为 `delta-plan-v1`，外层仍为每包一次模型调用，不增加多轮 agent 流程：

```json
{
  "protocol": "delta-plan-v1",
  "deltas": [],
  "quantity_accounting": []
}
```

执行器顺序固定：

1. 解析协议，检查输入引用和结果声明；区分模型新增结果编号与伪造输入编号。
2. 按回答顺序模拟全部拓扑操作，得到最终活组；所有取值操作必须引用最终组。
3. 建立候选字段否定视图和最终组空值决定。
4. 按显式引用依赖计算求和读法；表达式必须无环，不能引用未声明结果。
5. 收集并校验字段绑定；无竞争时生成成品视图，显式选择优先于默认补空，显式空值最高。
6. 展开最终读法叶子，检查观测交代、重复计数和既有来源资格。
7. 生成 COB、字段溯源、冲突与金额检查；不再重新选择已明确绑定的结果。

同类操作不再整体排序；模型也不需要把所有 `exclude` 都挪到 `split` 前面。
拓扑与取值分阶段，使 `fields_reject` 不必抢在 `sum` 文本位置之前，但执行时始终能使不可用叶子失效。

### 6.2 校验、重试与提交

结构合法不代表业务正确。`confidence` 仍只留痕，不决定接受、拒绝或优先级。

建议先完整模拟和校验，再提交，避免“先排除成功，后面拆组失败”造成半套计划：

- 解析失败或引用错误：把具体错误及编号返回给模型，最多重试一次，沿用现有调用重试上限。
- 重试后仍失败：按依赖连通分量提交。共享被消费组、最终组、绑定字段或计量叶子的操作属于同一分量。
- 一个分量失败时，其拓扑、排除、计算和字段修改全部回滚到该分量涉及的原始基线组；
  不能保留前半个 `exclude`，再用后半个默认价格顶上。
- 与失败分量独立的组可以提交。无法可靠建立依赖的错误，回滚整包模型计划。
- 回退必须标为 `unverified_fallback`，整体进入 `partial`，不能把回退基线说成模型确认结果。

失败分量的候选及拟议操作仍留在审计中。规则不替模型补一个拆组、求和或字段搬运决定。

### 6.3 默认行为的边界

默认基线仍可用于召回和故障回退。模型成功路径中，没有显式选择的组内非计量字段可以沿用现有协调顺序补空，
冲突照常保留；但显式否定、选择不得被默认协调覆盖。
多行计量不能通过默认单行读法绕过第 5 节。
排除行的两条自动捐赠路径、包金额自动当单标的总价、对账改选显式读法，在模型成功路径中均撤掉。

`llm=None` 的离线旧基线路径可以保留，便于历史对比，但应清楚标为 `legacy_baseline`。
不能用旧路径的通过结果证明新协议已经实现，也不能在模型失败时静默继承旧路径的内容推断并声称新协议已确认。

## 8 跨文件、跨表与重叠清单的表达能力

| 场景 | 操作组合 | 需要模型判断的内容 |
|---|---|---|
| HTML 项目全称＋附件多个详细标的 | 排除整体行；保留/拆分详细组；定向补描述字段 | 整体与组成关系、哪些属性是共有属性 |
| HTML 汇总数量＋附件展开明细 | 合组；附件求和；绑定求和；HTML 声明重复于汇总读法 | 是否覆盖同一批采购，有无遗漏明细 |
| 不同表分别列不同安装地点 | 合组；求和；绑定 | 地点是否独立、是否存在重复的小计 |
| 两个附件完整重复同一成交清单 | 合组；选一套或其汇总；另一套逐项或整体声明重复 | 两套清单是否同一采购范围 |
| 两个附件部分重叠 | 合组；选择无重叠叶子求和；重叠叶子声明重复 | 明细锚点与实际覆盖交集 |
| 同名但型号、单位或单价不同 | 命名拆组；各自配置读法 | 是否需要不同输出单元 |
| 同一对象多个矛盾报价 | 合组；明确选用；其他观测声明备选 | 哪份为有效成交观测，冲突是否可解释 |
| 需求文件提供规格、成交清单提供价格 | 需求行可排除；指定规格来源；价格只选合资格来源 | 描述字段是否适用于该成交标的 |
| 数量范围无法判清 | 留未决；描述可输出，完整数量/总价不冒填 | 目前证据不足在哪里 |

示例：假设 `c:html_summary`、`r:attachment_sum` 都是输入/计划中存在的引用，选择附件求和后可声明：

```json
{
  "group_id": "g:device",
  "observation": "c:html_summary",
  "relation": "duplicate",
  "of": "r:attachment_sum",
  "reason": "HTML 汇总和附件逐点明细覆盖相同设备与点位，数量一致"
}
```

这比“提示词提醒不要重复”多了一项可落地决定，但仍依赖模型看得到覆盖范围。
若一条候选把多个型号或多个计价项压成无法分解的字符串，本设计的 `split` 只能拆候选集合，不能凭空拆出新的原始观测。
该场景应保留未决，不能把本方案宣传为已经解决任意单行多实体的上游抽取错误。

## 9 模型输入：只补已经存在的证据

每包输入继续包含候选及字段状态、基线组、价格读法、报价资格、原文来源、包金额和公告概要品目。
同时把当前已收集却没有充分发给合并模型的 `MergeEvidence` 内容按包透传：

- 可直接关联的表标题、表头、章节、已有行文本及字段原列单位。
- 已解析附件页的已有文本和表头，带文件、页号与来源角色。
- 已有报价主体、中标主体及候选资格原因；`rule_suspect` 继续只是模型输入标记。

只使用已经存在于内存或运行产物的证据，不重启 OCR、不重读附件、不根据文件名猜采购范围。
能够按现有结构键直接关联时关联；同一来源中有多个可能表、可能行时保留整个相关上下文和歧义，
不能靠新的相似度阈值或关键词匹配假装找到了唯一原文行。
若上下文超限，应显式报告证据受限并留下未决，不能悄悄截掉部分候选再声称全量判断。

现有限制：终端管理器十条候选的 `row_text` 全为空；HTML 按名称唯一匹配的回填方式没有保留稳定行锚点。
如果已有 evidence 里还保留原表文本，可以补进第 8 步输入供模型判断；若没有，最后一步不能凭空恢复行序、点位或明细编号。
将来给上游候选增加稳定表行/单元格定位可提高可靠性，但不属于本次“只改第 8 步”的方案。

## 10 调用、金额检查与下游兼容

### 10.1 调用条件

建议有 COB 候选的包都进行一次合并与字段归属判断，保持现有失败时最多重试一次；没有 COB 候选则无需调用。
这样单标的服务可以否定误填规格，单标的包也能使用已有品目补全能力。
调用次数会增加，成本应按真实 token 与耗时记录；不承诺与当前跳过路径成本相同。
不按“服务”关键词另开规则，不把内容判断藏进调用门槛。

### 10.2 包金额是检查证据，不是数量关系裁决器

模型可参考本包金额，但最终明确的明细关系和来源绑定不能被 `_arbitrate()` 以差额更小为由改掉。
对账继续记录溢出、短缺与金额来源，按既有精度做算术体检；不新增阈值，不要求所有清单必须凑齐包金额。
金额不一致时保留冲突或未决，不能因此断言某一行是重复或把一个整项价格分摊给多个对象。

### 10.3 不改第 8b 步也必须约束它能看见的备选

第 8b 步会在金额溢出时从 `merged.alternatives` 选择读法，可能覆盖第 8 步价格。
因此新模型路径不把与最终绑定竞争的读法放入该可执行备选集合。
候选全部读法、模型声明的冲突备选仍完整进入 `merge_decisions/conflicts` 审计，不能为了保护决策丢掉证据。

最小实施建议：新协议已处理的组不向第 8b 步提供可改写价格的选项；第 8b 步继续检查和报告，不能撤销新计划。
旧基线路径仍按旧接口提供备选。若以后需要让第 8b 步重开决定，必须显式重新判定并审计，另行设计与批准。

`Project/COB` 公开字段不变；使用现有泛型 `merge_decisions`、`conflicts`、`merge_notes`、`provenance` 承载协议与溯源。
`provenance` 保留现有读取所需的候选编号，详细计算树和逐字段来源存入 `merge_decisions`，避免改变数据库/页面的读取假设。
需要验证入库后的 raw JSON 能保留这些记录，不能仅验证运行目录里有审计文件。

## 11 审计：合法、执行和成品采用分别记录

每条操作建议记录：

| 状态/内容 | 含义 |
|---|---|
| `validated` | 引用、参数、资格和算术检查通过 |
| `applied` | 对计划视图发生了实际改变；幂等操作可为 false |
| `used_in_final` | 最终 COB 的字段或成员确实依赖此操作 |
| `rejected_reason` | 明确的拒绝原因和涉及编号 |
| `blocked_by/rolled_back` | 因依赖失败未执行，或随分量一起回滚 |
| `sources/leaf_ids` | 原始候选来源与计算叶子，不只留一个拼接字符串 |
| `field_bindings` | 每个显式输出字段的来源、模式、否定和派生关系 |
| `quantity_accounting` | 已计入、重复、备选和未决的完整展开结果 |

例如一个 `sum` 可 `validated=true, applied=true, used_in_final=false`，因为另一个读法被明确选用。
不能只统计 accepted 次数便说求和成功，也不能把截断的思考摘录当成可执行决策。
模型的自然语言理由供复核；程序只读结构化决定及其已有来源事实。

## 13 验收方案

设计稿阶段不运行新协议测试，因为执行器尚不存在。实施后分开验证协议正确性和模型决策质量。

### 13.1 用人工计划或假模型验证执行器

1. 终端管理器十行必须能在一次回答中拆成两个命名组，分别求和并绑定，输出10台与6个及对应金额。
2. P10的相同数值不同叶子全部可计入；嵌套求和中的同一叶子重复必须被拒绝。
3. `merge→split→merge` 可正确执行；旧组引用、未知候选、重复结果名、漏成员、重复成员、循环读法必须报错。
4. 模型只选3个而未交代其他明细时不能输出完整3个；声明重复但已知数值矛盾时必须转为备选/未决。
5. 需求报价和非中标人报价不能经 `sum`、跨组来源或部分字段绑定绕过供价资格。
6. 排除整体行可显式给指定详细组补共有字段；不点名的组、字段不能收到捐赠。
7. `fields_reject` 后不能被 raw 回退、组内补空或后续捐赠复活；原始候选保持不变。
8. 绑定的求和不能被金额对账或第 8b 步换回单行；金额差异必须仍能报告。
9. 一个依赖分量失败须整体回滚，独立分量不受影响；回退和未决必须落入 partial 和审计。
10. 三个服务包即使单行也有模型判断入口，规格可为空；合法服务规格不能被“服务一律无规格”的规则清空。

### 13.2 旧运行产物回放与人工核对

直接使用 `online-runs/` 中已有 `08_normalized_candidates.json` 与 `08b_merge_evidence.json`，不重跑附件链路。

### 13.3 达标判断

验收要求是：原语能够表达预期计划，执行器忠实落地，不让数量静默丢失或字段自动越界；
在证据充足的实际案例中，模型分配这些原语的正确率提高。
协议不承诺解决已经丢失行锚点的所有歧义，不以“结构校验通过”代替业务事实核对。
若实际未决率过高，应先检查输入证据是否足够，再讨论输入补传递，不能撤掉覆盖检查换取表面上的完整率。
