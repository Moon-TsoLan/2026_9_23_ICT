# 主路线实现细则

## 合并挂起与资源边界（2026-11-12）

`pipeline.announcement_chain`保留原处理链的局部变量，只在调用`merge_projects`前yield一次。`run_announcement`同步驱动此链；`run_batch`、`worker.run_loop`和20例运行器使用`MergeScheduler`。前半程提交执行器前取得名额，仅推进第一次；asyncio等待独立合并池，返回结果或异常后立即提交专用接续池，执行原链的send/throw并接续修复、产品供应方补全、最终政策及落盘。接续池不借给前半程，不凑批、不等待计时窗口。合并内部的按采购单元调用、SUB合并、思考开关及一次协议修复保持。

| 配置 | 默认 | 约束 |
|---|---|---|
| ICT_ANNOUNCEMENT_WORKERS / --threads / --workers | 4 | 前半程名额；设1仍允许与合并、接续交叠 |
| ICT_MERGE_WORKERS | 4 | 独立合并协调线程数，不直接代表API请求数 |
| ICT_RESUME_WORKERS | 1 | 独立接续名额；空闲不借给前半程，不增加活跃案例上限 |
| ICT_LLM_MAX_CONCURRENCY | 8 | 所有阶段共享的实际请求上限 |
| ICT_LOCAL_HEAVY_WORKERS | 2 | 原本地重活闸门 |
| ICT_PARSE_MAX_INFLIGHT | 3 | 原OCR文档在途上限 |

活跃案例上限为普通名额+合并名额，包含排队合并与等待接续的案例，避免全部公告都读入内存后等待。合并协调池与执行按包模型任务的既有LLM_POOL分开，避免父任务占满子任务所需线程。同步HTTP请求由合并线程接收，等待它的协程挂起；在途请求仍占API名额，网络返回不被暂停。API满载时新公告仍可能排队，实际吞吐不能由挂起设计本身保证。

worker只领取当前前半程可启动且未超总活跃上限的数量，其余保留waiting。领取操作放入独立单线程控制池，完成通知由事件循环处理，不占前半程或接续池。同一任务所有项共用当前内存对象；worker内部读任务/写任务共用同一把可重入锁，避免控制线程与接续写回竞争，不改变跨进程文件写入行为。旧批未完成时继续轮询新任务。`--once`排空可领取任务并等待已启动链结束。提取失败不入库，入库成功后才清理；保留原有中断标记，不加新生命周期。

`run_state.merge_wait`只有queued/running/resuming/null，只用于进度显示，不送模型、不参与判定，也不增加阶段。前端保留三个阶段并显示接续等待秒数。run_state及10报告新增固定四项merge_timing：queued_at/started_at/returned_at/resumed_at，ISO8601带时区、毫秒精度，未到达为null；compare_times.py输出merge_timing.csv，分别统计合并排队、函数执行（含内部任务排队/SUB合并）、接续等待。旧记录缺失不补零。9阶段和数据库/三表结构不变。

2核4G部署建议前半程2、合并12、接续1、API24，总活跃最多14；既有配置值不自动改写，仅接续缺省为1。控制池固定1个轻量线程。Windows跨进程JSON替换和MuPDF线程安全问题不在本次实现中修复，仍归唯一待办；真实复测必须单列这些故障。

离线验证检查只有合并能让出名额、活跃案例和合并数有界、失败接续、无提前清理、同任务状态不被覆写及旧任务未结束时领取新任务；同步与批处理的固定回答成品、证据和调用计数一致。真实API/OCR、同20例吞吐及内存峰值尚未复测。本节覆盖下文历史执行方式说明。

2026-11-08，当前契约v1.6；第8步规范v10、delta-v5执行算法保持。此前实现细则见[历史快照](archive/主路线实现细则-v1.5-修复前.md)。本轮授权范围与例外以[AGENTS](../AGENTS.md)最新记录为准。

## 入口与数据流

pipeline.run_announcement调用s01_understand.read_announcement：summary/body两个完整HTML请求并行，正文同时返回采购单元与候选。结构读取为HTML提供机械来源编号，不按章节、表角色或行数裁内容。两路项目身份正文优先、概要补空。封装一次分配内部引用，再计算一次只读needs。

当前summary-v2/body-v4由局部AnnouncementReceiver接收：身份/目录是父结构，其余观测逐项使用现有候选接收检查；金额与表注释各自校验。父目录首次合法后固定，拒绝跨修复重排。接收错误给原值、路径及类型/枚举，最多一次修复；合法项保留，未修复项审计并partial。接收器只存在于这一次调用中，不是统一state或任务关闭组件。字段说明从既有类型/配置的相同枚举导出，四份前半程协议递归核对输出形状。

s04_attach.process_attachment_pages以嗅探容器读取。原生内容按attachment_pages.split_page切分，正文和全部表行不截尾；DOCX按XML段/表顺序，XLSX保留全部工作表与行。原生可用时直接抽取，候选为空不代表失败。

PDF图像页、无文字页和图片逐页调用screen-page-v7；输入同时带本页原生文本。模型选择extract/ocr/skip，confidence不参与判断。既有两项硬忽略保持。旧Office及含图DOCX在本地LibreOffice转换后再按页处理，坐标标rendered_office_page；转换失败记录错误，不自动上传整文件。

页输入带公告合法候选的known_observations固定快照：编号、实体、采购单元、非空原文/必要状态、引用；每页相同，不并入附件发现。业务增量包括当前缺口之外的有效字段。页类别、图片有字不等于有业务价值；模型reason解释具体信息及读取方式，代码不读reason做内容判断。14/19旧参考使用偏缺口口径，不能当新版本必须跳过的标签。

只对模型选择的页向原ParseQueue/ParseClient提交pages。OCR后使用attachment-extract-v8直接抽取，没有第二轮页摘要筛选。每个来源只以实际读取方式生成一套候选；原生与OCR不重复入链。格式错误沿用complete_json一次修复；接口失败或最终格式失败不会变成OCR决定。

所有附件观测收集结束后，按需调用既有bind_packages一次，新HTML来源及附件片段一并传递。然后调用未改的归一化、合并、修复与自供代码；最后supplier_policy.finalize_suppliers只应用已经批准的两项SUB默认政策。

## 状态、接口和审计

不使用共享大state。运行载体为公告骨架、既有Candidate/Amount及原文证据、只读ProjectPlans.needs和07页处理记录。删除原生解决通道、前后需求快照、覆盖状态、文件复核、字段命中门和检索词传递。

需求保留field/package_no/reason/target_entity，必要时带已有候选及供应商名。发现与补已有对象由实际目标和reason说明；不再声明完成状态，不限制抽取新对象。缺口计算保留原覆盖率与服务可选字段，仅按共同政策排除已有可补报价和审查默认值。

9个有效提示词在fields.py显式注册。截至2026-11-10：announcement-summary-v2、announcement-body-v6、screen-page-v9、attachment-extract-v10、package-binding-v5、merge-objects-v9、merge-subs-v3、repair-package-v1、supplier-completion-v1。合并v9仅明确操作供值键、既有资格、枚举及品目引用，示例在fields.py单一维护；执行协议和算法未改，39项离线测试通过，真实效果未复测。历史字段块另存冻结JSON，不在当前定义中进行版本继承。普通字段只输出原文标量，完整观测壳由程序建立；模型原文金额、表头单位分开，现有解析器负责换算。正文固定正常输出容量16384，两次相同，其它阶段不改；finish_reason只审计，不触发扩容、续写或OCR。

注册阶段及文件名以state.STEP_FILES为准，共9阶段，03b按需执行；08b为证据通道。01记录两路答复、冲突及调用信息；07记录每页决定、抽取、失败与未覆盖；08保留原值/规范值；09保留既有合并审计及最终政策来源；10记录各调用耗时和usage。历史文件只读兼容，不为新运行产生旧空阶段。

预算仍为解析40/文件、抽取30上下文/文件和100/公告，长PDF结构排名不变。分片使用既有6000字符上限，原生逻辑片段不假称物理页。selected_pages为所选抽取上下文，parsed_pages为实际OCR返回页；uncovered_pages与failed_pages明确报告，未覆盖不报success。

OCR跨页表的返回页号仍可能是合并记录锚点，不能据此证明所有行原始物理页。来源全文在08b按原编号提供；模型不能绕过已有候选直接供业务数值。

## 政策与验证

候选保留原文明示报价、成交份额和审查状态；最终明确报价优先，缺报价中标人可用其明确供应商成交金额，未明确失败的已确认主体默认通过。已有冲突未决保留。政策补值写入现有field_bindings；不修改三表或数据库结构，不回填旧库。

固定回答覆盖两路并发与全文、同号不同类型、精确来源、后续表/工作表、空抽取、页门失败不扩OCR、预算和政策；原后半程测试继续运行。被删除流程的旧断言由新契约测试替换，测试数量与历史版本不可直接比较。

政策离线比较入口：`python -B eval/replay_supplier_policy.py`。默认读取已有50例成品及冻结金标，输出work/front-half-20261108/policy-only；不覆盖来源。输出原/新政策分组指标、补值及来源哈希。历史目录无合并审计，不能恢复历史未决；不复用不属于当前输出顺序的人工行号。

用户已授权API复测，首轮47/50和紧凑协议49/50的完整结果保留，固定输出容量版另存目录；未调用OCR或数据库。各轮输出容量与字段表示差异明确标识，不宣称同预算提速。后续质量保持且总耗时/费用改善才通过；历史50例诊断、holdout25最终验收。唯一待办出口为[待优化清单](待优化清单.md)。
