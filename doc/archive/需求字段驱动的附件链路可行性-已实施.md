# 需求字段驱动的附件链路：可行性

日期：2026-10-03。状态：**设计与测算，未改任何代码**（规则冻结中，见 `AGENTS.md`）。
触发问题：济宁那则公告 HTML 没有包金额、附件里手写有 A/B/C 三包成交金额，但链路里没有任何一步把"我们缺什么"告诉模型。

---

## 1. 断点在哪（逐个接口核对过代码）

| 接口 | 实际载荷 | 有没有"需求/缺口" | 结论 |
|---|---|---|---|
| 第 4a 名录 | 容器、页数、digest、可读性 | — | 结构事实，正确 |
| **第 4b 目检** | `{file_name, format, pages, table_headers, content_view}` | **没有** | 模型不知道我们在找什么，只会按 `kind` 六分类 |
| 4b 输出契约 | `{kind, has_price_table, header, confidence}` | **没有表达位** | 即使它看到包金额，也没有字段可写 |
| **第 5 步定位** | `{known_packages, search_queries, files[页摘要]}` | **没有**（只有检索词，且检索词来自 HTML 标的名） | 与第 3 步的缺口清单完全脱节 |
| 第 6 步抽取 | `current_package{project_id, package_no, missing_fields}` | **有** | 唯一传了缺口的地方 |
| 第 3 步规划 | `field_stats` 只覆盖 `COB_FIELDS` 的 11 个字段 | **不追踪包金额** | "缺包金额"这个事实根本没被记录，后续无从传递 |
| 包金额来源 | 第 1 步模型 + `fill_package_amounts`（HTML 正文锚点） | 只从 HTML 来 | 附件里的金额**没有落点** |

所以你的判断成立，而且要补两处：一是 needs 没往下传（4b、5），二是 needs 本身算不出来（第 3 步不追踪包金额、目检输出没有承载位）。

## 2. 设计：一个 `needs` 对象贯穿三步

```
needs = [ { field: "package_total_amount", package_no: "A", reason: "absent" },
          { field: "unit_price",            package_no: "B", reason: "points_to_attachment" },
          { field: "spec_model",            package_no: "B", reason: "coverage_lt_0.3" }, ... ]
```
- **来源**：第 3 步产出（把 `field_stats` 扩到包含 `package_total_amount`、`winner/score` 这类包级与主体级目标）。
- **注入点**：4b 目检、5 定位、6 抽取三处 payload 都带上"本包需要哪些字段"（只给字段名+原因，不给规则解释）。
- **4b 输出契约扩展**：
  ```
  {"kind":"...", "found_fields":["package_total_amount","total_price"], "found_count":2,
   "header":"...", "confidence":0.9}
  ```
- **判定改为**：`found_fields ∩ needs ≠ ∅` → 版面解析；否则判负；`confidence < 0.6` 一律解析（保守保留不变）。
  这**取代** 现在的 `KIND_PARSE` 三类白名单，属规则替换，需你批准。
- 目检"提供不全"是预期内的（你也这么判断），所以 `found_fields` 只作为**准入证据**，不作为内容；内容一律来自 4c。

## 3. 包金额的落点（这里有一个必须防住的坑）

不能新增候选类型（契约只有 cob/sub），也不能把它塞进行字段（会污染每行）。建议：

- 目检与解析产出**文件级观测** `package_amounts: {"A": 1930000, "B": 1486000, "C": 486000}`，存在 `05/07` 的 side-channel 与候选层之外的 `observations`。
- 第 8 步的使用规则：
  1. 只在该包 `package_total_amount` 为空时填补，记 `repairs: package_amount_from_attachment`、`source`、`confidence`；
  2. **绝不参与对账换组**——否则同一份附件既提供行价又提供总额，8% 偏差检查变成自证，失去唯一的外部校验；
  3. HTML 已有金额时只作**差异告警**（`amount_disagreement`），不覆盖。
- 手写体可信度实测：同一页 200 dpi 读对（A/B/C 全对），300 dpi 把 C 包 `486000` 读成 `436000`。所以该值只能当"填补/告警"，不能当"权威"，且必须进 `review_required` 触发条件。

## 4. "记忆"与成本：不必累积对话

现状已经是"每步只带当步需要的结构化片段"，这是对的；只要把 `needs` 也当作这种片段传下去，就不需要把上一次模型输出整段搬进下一次上下文。

| 项 | 现值 | 加 `needs` 后 | 增量 |
|---|---|---|---|
| 4b 目检单次输入 | 1.1k–1.4k token | +30～70 token | ≈ +4% |
| 每则目检次数 | ≤8 唯一文件 | 不变 | — |
| 每则目检 token | ≈ 9k | ≈ 9.4k | +4% |
| 第 5 步单次 | 约 1.5k–4k | +120 token | +3% |
| 目检时延 | 0.9 s/次 | +0.05～0.1 s | 可忽略 |
| 全量目检成本 | ≈ 9.4M in token | ≈ 9.8M | +0.4M |

真正的成本风险不在 token，在**解析量**：判定条件换成"命中 needs"后放行的文件会变多。**文件数已按用户 2026-10-03 指示不设上限**，于是唯一的闸门只剩页数：每文件 `PARSE_MAX_PAGES_PER_FILE=40`，放行 N 个文件最坏 40N 页 ≈ 3 分钟×N（真服务实测 4.45 秒/页）。原先提的"排序键改命中 needs 项数"随截断一起作废——排序不再丢弃任何文件，只决定处理先后；全量若出现耗时过长的公告，按你的意思届时再做专项优化。

## 6. 验证方案（避免又一次对着 10 则调规则）

1. **影子跑**（P0，不改判定）：10 则金标各跑两遍——现行 vs `needs` 注入版，只比较：4b 的 `found_fields` 与实际 4c 解析后能补上的字段是否一致、放行文件集合差异、页数成本差。产物落 `work/shadow/`。
2. **holdout25 全量**：留出集只跑 `needs` 版，看三件事——补上了多少原本缺的字段、复核率变化、每则页数与墙钟分布。这里没有金标，用覆盖率+人工抽检 5 则。
3. **回归门禁**：benchmark10 必须保持 74/74 名称、中标人与包金额不退；`checks` 不新增 hard。
4. 分期：P0 传 `needs` + 输出 `found_fields`（纯观察）→ P1 换判定 → P2 包金额 side-channel → P3 调排序。每期间隔一次留出集验证。

## 7. 结论

可行，且**不需要引入对话式记忆**：`needs` 是一个几十字节的结构化对象，注入三处 payload 的成本约 +4%。真正的设计要点只有一个——**附件来的包金额不能反过来当对账基准**，否则第 8 步唯一的外部校验会自我印证。改动共 8 项、全部落在规则/契约面上，按 `AGENTS.md` 需要逐条批准；建议先做 P0（只观测不改判定）拿到影子数据再决定是否切换。
