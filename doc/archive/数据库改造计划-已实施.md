# 【已实施·已归档】数据库改造计划（项目编号 + 包号 + 轮次）

日期：2026-10-07 　范围：**仅入库侧**（`db/001_schema.sql`、`db/load_runs.py`）
　状态：**已实施并验证**（见 §8）
　归档：2026-10-07，实现已合入；结构以 `db/001_schema.sql` 为准，本文只作决策记录。

## 0. 一句话

把 `project` 的唯一键从「项目名 + 包号」改为「**项目编号 + 包号 + 轮次**」；轮次只在同一（项目编号, 包号）被多则公告复用时才大于 1。其余 99.7% 的包轮次恒为 1，键与展示效果不变。

配套一处最小流程改动：**第 1 步的 payload 要带上“项目编号”标题对应的值**（见 §2.4）。该值只用于喂模型，不参与任何判定。

---

## 1. 为什么现在的键不够

当前 `project_id = <项目名>|<包号>`（`src/ict/ids.py:make_project_id`），有两个毛病：

1. **同名不同项目会被错并。** 二次招标、重新采购时模型抽到的项目名可能只差一个“（二次）”后缀，甚至完全一样。
2. **包号只在单则公告内唯一。** 重新采购时公告常把包号从 `包1` 重新编号，同一个（项目编号, 包号）在两则公告里可能指向不同内容。

改用「项目编号 + 包号」能解决第 1 条，但解决不了第 2 条：实测存在同一（编号, 包号）出现在多则公告、且内容/中标人不同的情况。补上「轮次」这一维即可。

## 2. 数据实测依据（全量 1038 则公告）

### 2.1 每一则公告都有项目编号

早先的“33 则无编号”是诊断正则过严导致的误报，原因包括：

- 标签带括号或空格：`一、项目编号（政府采购计划编号）：…`、`项目 编号：…`、`项目编号（或招标编号…）：…`
- 编号里含 `/`、`[]`、中文：`ZWSW-2025-12-02 /NXHZ-CG-2025-21`、`[231201]ALAZ[CS]20260001`、`FS34000120264452号`
- 标签后没有冒号：`一、项目编号 SDGP370203000202602000053`
- 编号值过长、超出诊断正则的截取窗口

放开标签后复查：**1038/1038 都有“编号”行**，无真实缺失。

### 2.2 跨公告同 (编号, 包号) 的真实情形

全量里同一编号被多则公告共用 15 组，逐条核对后：

| 类型 | 组数 | 是否冲突 | 说明 |
|---|---:|---|---|
| 包号互不重叠（真正的“包分散在多公告”） | 多组 | 否 | 第 1 步只建本公告有中标人的包，键天然不重叠 |
| 同键不同内容/中标人 | **3 组** | **是** | 本次改造要解决的 |
| 诊断口径误判（按正文提及包号统计） | 2 组 | 否 | 见下 |

**3 组真实冲突（本方案的测试夹具）：**

| 项目 | 项目编号 | 第一轮 | 后续轮 |
|---|---|---|---|
| 口腔医学智能创新研究平台 | `GZGK25D382A1284Z` | `t20260206_26154814` 包1(口腔种植手术机器人) | `t20260311_26256690` 包1(数字化口腔扫描智能终端) |
| 大数据实训室设备采购项目 | `441901-2026-00902` | `t20260402_26352885` 包1(广东三胜) | `t20260612_26743079` 包1(北京智谷星图) |
| 第二批实训室电脑更新项目 | `441901-2026-01878` | `t20260511_26545663` 包1(智能制造学院及卫生健康学院) | `t20260604_26688741` 包1(创意设计/通识/国际交流)、包2(商学院等) |

第二批实训室最能说明“不能简单取最新”：第一轮包1（广东瑞普，693.9 万）很可能是仍然有效的独立结果，重招只是把其它学院的包重新编号，两条都要保留。

**2 组误判（已用第 1 步实测排除，见 `work/_pno_check/step1.py` 输出）：**

### 2.3 编号是否进入模型输入

对第 1 步实际发送的 payload 做了确定性检查（不调模型）：33 则疑似样本中 **31 则的编号值已进入 payload**，模型可见。剩下 2 则 payload 里只有标题“一、项目编号”、没有数值，模型可能返回 null：

- `t20260610_26721304`（安徽省突发事件预警短信发布信息传输服务项目（1包））
- `t20260806_27082279`（市北区电子政务外网链路接入及网络运维服务项目）

随后对这两则实跑第 1 步，**确认模型返回 `source_project_no = None`**：

| 公告 | 第 1 步输出 |
|---|---|
| `t20260610_26721304` | 编号 `null`；包1(移动包)、包2(电信包)、包3(联通包) |
| `t20260806_27082279` | 编号 `null`；包A、包B |

即：改造前，全量 1038 则里 **1036 则能拿到编号，2 则拿不到**。方案必须带兜底键（见 §4）。

### 2.5 编号抽取放宽后的实测（已实施）

`PROJECT_NO_RE` 放宽到「标签 + 可选括号说明 + 可选冒号 + 值（允许 `/`、`[]`、`（）`、中文）」，
并对不平衡的尾部右括号、纯中文值做清理。全量 1038 则对比：

| 项 | 数量 |
|---|---:|
| 结果不变 | 963 |
| 结果变化（其中原为空→有值 **64** 则，原有用→为空 0 则） | 75 |
| 仍取不到 hint | 4 |
| 这 4 则的编号值都在 payload 里（走 `html_headings`），模型因此仍能看到 | **4 / 4** |

实跑第 1 步确认修复生效：`t20260610_26721304 → FS34000120264452号`、`t20260806_27082279 → SDGP370203000202602000053`、
`t20260203_26146674 → KSHZX（GK）2026-002`（旧为截断的 `KSHZX`）、`t20260604_26684133 → XJJTHY(GK) 2026-04`。

剩下 4 则 hint 仍为空，是因为它们的编号不挂在"项目编号"这个标签下：

| 公告 | 原文写法 | 实测模型输出 |
|---|---|---|
| `t20260309_26247691` | 标题本体就是编号：`一、 SDGP371503000202602000002`（另有"聊城市公共资源交易中心系统内编号：XCPZFCG-2026-006"） | **`SDGP371503000202602000002`**（包A/B/C） |
| `t20260707_26883491` | 名称与编号同标题：`三、采购项目名称及编号：…（…）( SDGP370500000202601000048 )` | **`SDGP370500000202601000048`**（单包） |
| 山东两则 | `项目编号： 山东省政府采购网：SDGP… 德州市公共资源交易网：DZSSXZC-…` | 值已在 payload，模型可读 |

结论：**这 4 则不需要兜底键**——`html_headings` 已经把标题原文送进 payload，模型照常抽得到。
因此不再为此加正则（按"无必要不添加规则"）。

### 2.4 第 1 步 payload 补“项目编号”的值（已决定的小改动）

DOM 结构有两类：

| 结构 | 占比 | 现状 |
|---|---|---|
| 编号值直接写在标题元素里，如 `<h4><strong>一、项目编号：440001-2026-27404</strong></h4>` | 绝大多数 | 已随 `html_headings` 进入 payload |
| 标题只有标签，值在**后面的兄弟节点**里（`<p><strong>一、项目编号</strong></p><p>…FS34000120264452号…</p>`、`<h3>一、项目编号</h3><div class="notice-content"><u>SDGP…</u></div>`） | 实测 2 则 | 未进入 payload |

**改动**：把 `src/ict/html_context.py` 里生成 `source_project_no_hint` 的那条抽取（`PROJECT_NO_RE`，第 19 行）放宽，使“项目编号”标题后带值的情况都能取到。该字段**已经**在 payload 里（`step1_payload` 的 `source_project_no_hint`），因此不需要新增字段，也不需要改 `fields.py`。

**成本**：只有当前 hint 为空或被截断的公告（约 70 则，≈7%）payload 字节会变；其余 97% 的请求与今天完全一致，不受影响。若用 cassette 做回归，需要重录这约 70 则的第 1 步。

## 3. 改造方案

### 3.1 键的定义

| 概念 | 定义 |
|---|---|
| `package_key` | `<项目编号>\|<包号>`；无编号时用兜底键（§4） |
| `round_no` | 同一 `package_key` 在全部公告中按公告日期升序的序号，从 1 开始 |
| `project_id` | `round_no = 1` 时为 `package_key`；`round_no > 1` 时为 `<package_key>\|r<round_no>` |

关键性质：**只有 (编号, 包号) 跨公告重复时才会出现 `round_no > 1`。** 其余情况下 `project_id` 与今日形态一致，下游查询与星图节点 id 不变。

### 3.2 DDL 变更（`db/001_schema.sql`）

```sql
CREATE TABLE project (
  project_id           text PRIMARY KEY,             -- <package_key>[|rN]
  package_key          text NOT NULL,                -- <source_project_no>|<package_no>，缺失时见 §4
  package_no           text NOT NULL,
  round_no             int  NOT NULL DEFAULT 1,      -- 同 package_key 的第几轮
  source_project_no    text,                          -- 项目编号（模型抽取；可能为空）
  announcement_id      text NOT NULL REFERENCES announcement(announcement_id) ON DELETE CASCADE,
  project_name         text NOT NULL,
  purchaser            text,
  package_total_amount numeric(18,2),
  UNIQUE (package_key, round_no)
);
```

说明：

- 保留原有 `UNIQUE (announcement_id, project_name, package_no)` 亦可（同公告内包号不会重复），非必需。
- `round_no` 用 `int` 而非布尔/标记：轮次是重招的固有事实。
- **不新增 `is_effective` 之类的标记**（按用户指示：无必要不添加标识或步骤）。

### 3.3 入库逻辑变更（`db/load_runs.py`）

`load_run()` 目前按 `project["project_id"]` 直接写 `project`。改为：

```
1. 读入本批全部 run 的 09_merged_projects.json，收集每个包：
      base_key = f"{source_project_no or fallback(§4)}|{package_no or '1'}"
      pub_date = 公告 id 前缀的 tYYYYMMDD（announcement.created_at 是入库时间，不能用）
2. 按 base_key 分组，组内按 (pub_date, announcement_id) 升序
3. 组内第 i 项：
      round_no   = i
      project_id = base_key            if i == 1
                 = f"{base_key}|r{i}"  if i > 1
4. 以新的 project_id 写 project；cob / bid / supplier 的写入逻辑不变
```

约束与注意：

- **批量重灌**：`load_runs.py` 用 `--reset` 全量重灌，轮次在同一批内计算即可保持一致；增量补灌时需先查库内同名 `package_key` 的最大 `round_no` 再续号。
- 排序依据用**公告 id 里的日期戳**，不要用 `announcement.created_at`（那是 `DEFAULT now()`，等于入库时间）。
