# 可视化分析检索平台 · 前端展示与逻辑设计方案

- 版本：v1（讨论稿）
- 日期：2026-09-28
- 范围：赛题五 · 任务三「可视化分析检索平台」的前端部分（样式 + 逻辑）
- 不涉及：任务一抽取算法、任务二关系建模算法、后端入库实现（仅约定接口契约）

## 0. 先对齐：这个平台到底要交什么

先把赛题原文里的硬要求摊开，因为**每一条都直接决定界面长什么样**。

### 0.1 三大功能 = 赛题任务三的原文要求

| 你说的功能 | 赛题原文要求（任务三） |
|---|---|
| 功能 1 上传 + 文件树 + 抽取入库 | 「支持批量上传同规范标准的数据集进行自动化处理」「数据集上传后自动解析、实体抽取与结构化入库」 |
| 功能 2 高级检索 | 「提供标的物**全字段检索、筛选与查看**能力」 |
| 功能 3 可视化查询 | 「对接任务二关系模型，实现**五大业务场景的可视化查询、统计与结果展示**」「界面简洁可用、响应高效」「鼓励创新交互设计」 |

### 0.2 五大业务场景（赛题任务二原文，前端必须一一对应）

| 编号 | 场景 | 输入 | 输出 |
|---|---|---|---|
| **S1** | 采购单位 → 长期/大量合作的中标供应商、产品供应商 | 1 个采购单位 | 合作次数、交易总金额 |
| **S2** | 采购单位 → 高频投标主体 + 高频协同组合 | 1 个采购单位 | 高频（TOP5）投标主体、协同投标组合 |
| **S3** | 中标供应商 → 高频共同竞标主体 | 1 个中标供应商 | TOP5 共同竞标主体、全部参与投标主体（频次、总金额） |
| **S4** | 多个中标供应商 → 共同合作的采购单位 | 2..N 个中标供应商 | 交集采购单位、合作频次、合作金额 |
| **S5** | 多个中标供应商 → 共同竞标的项目与结果 | 2..N 个中标供应商 | 项目数量、项目总金额、竞标结果 |

### 0.3 评分中会直接影响前端的硬约束 ⚠️

| 评分项 | 分值 | 对前端的含义 |
|---|---|---|
| 查询效率 | **10 分** | **单次查询「前端发起请求 → 结果完全渲染完毕」＜ 1 秒得满分**；1–3 秒 7 分；3–5 秒 3 分；≥5 秒 0 分 |
| 平台功能完整性 | 5 分 | 任务一、任务二的功能都要能在平台上跑通（每项 2.5 分） |
| 技术栈合规性 | 5 分 | 必须是 **Vue + Python**（现有 `web/` 已是 Vue 3，合规） |
| 演示效果 | 10 分 | 「演示流畅完整、交互逻辑人性化」——演示视频要求完整跑通任务一+任务二全流程 |

**结论：这 10 分的查询效率不是"优化项"，是设计红线。** 所有交互设计都必须围绕"结果先出、装饰后补"来写。后面第 5 节会专门讲。

## 1. 三条线的边界（避免和队友撞车）

三条线并行推进时，前端只做"壳 + 交互 + 渲染"，算法与数据由另两条线提供。所以**先定契约、再写界面**是唯一的正确顺序。

```
┌─────────────┐   产出结构化 JSON    ┌──────────────┐   写入    ┌──────────────┐
│ 抽取流程线   │ ─────────────────▶ │ 入库/关联线   │ ────────▶ │  数据库       │
│ (任务一)     │  Project{cobs,subs} │ (任务二建模)  │           │ SQLite/Neo4j │
└─────────────┘                    └──────────────┘           └──────┬───────┘
                                                                     │ HTTP API
                                                          ┌──────────▼──────────┐
                                                          │  前端（本方案范围）   │
                                                          │  上传·检索·可视化     │
                                                          └─────────────────────┘
```

前端**不参与**抽取、不入库、不做关系计算。前端只做三件事：

1. 把文件传上去、把处理状态显示出来；
2. 把检索条件发给后端、把返回的行渲染出来；
3. 把关系结果画成图与表。

## 2. 视觉设计语言（样式）

现有探索稿是"浅色纸面 + 深色星空"两种气质并存。这个对比很好，正式版把它**体系化**成两个域，而不是两种随机风格。

### 2.1 双域主题

| | **记录域（Light / 纸面）** | **宇宙域（Dark / 星空）** |
|---|---|---|
| 用于 | 上传、检索、主体档案、结果表格 | 关系星图、场景可视化 |
| 气质 | 编辑部 / 档案柜：克制、精确、可读 | 天文台：沉浸、发现、空间记忆 |
| 底色 | `#fafafa` 纸白 | `#0c0b0a` 星黑 |
| 文字 | `#09090b` 墨黑 | `#f6efe6` 月白 |
| 分割 | `#e4e4e7` 1px 发丝线 | `rgba(246,239,230,.08)` |
| 强调 | `#ec4899` 品红（少量点缀） | 暖金 `#ffce94` |

**为什么坚持双域？** 因为两类信息的心智模型不同：查数据时你要"看清、比对、复制"，深色反而累；看关系时你要"沉浸、探索、发现异常"，浅色反而散。强扭成一种主题，两边都别扭。

### 2.2 字体与排版

```
标题（记录域）：Noto Serif SC   600   —— 给数据一点"档案感"
正文：         Inter + Noto Sans SC   —— 中英混排稳定
数字：         tabular-nums           —— 金额/数量纵向对齐，比对场景必需
星空标签：     Noto Serif SC         —— 与宇宙域呼应
```

金额、数量、得分**一律走 tabular-nums**（等宽数字）。这是数据平台最容易忽略、但最影响专业度的一点：等宽后一列数字的个位对齐，扫读速度快很多。

### 2.3 语义色板（关系星图）

| 角色 | 色 | 说明 |
|---|---|---|
| 采购单位 buyer | 米白 + 大光晕 | 体量最大，作为"恒星" |
| 项目 project | 暖橙 `#f0d0b0` | 行星球体 |
| 中标供应商 winner | 亮暖白 `#fff6ec` | 最亮 |
| 投标参与方 bidder | 灰白 `#efe4d6` | 半透明 |
| 产品供应商 vendor | 琥珀 `#f0d8bc` | 偏金 |

| 关系边 | 色 | 线型 |
|---|---|---|
| 合作（win / supply / buy） | 暖金 `#ffce94` | 实线 + 流光 |
| 竞争（同场投标 bid） | 冷蓝 `#c4d0e0` | 细实线，弱化 |

**关键点：合作与竞争必须用"色相"区分（暖/冷），不能只用明暗。** 因为这是本平台的核心洞察——一眼看出"谁和谁抱团、谁和谁死磕"。

### 2.4 设计令牌（可直接落地）


### 2.5 三条视觉纪律（避免探索稿里的"简陋感"）

1. **不用 emoji 当图标** —— 统一用 `lucide-vue-next`（项目已装），统一 18/20px。
2. **hover 只改颜色/透明度/边框，不做 `scale`** —— 缩放会引起布局抖动，显得廉价。
3. **数字右对齐 + 等宽；长中文名左对齐 + 省略号** —— 表格的行高与对齐一致，才像专业系统。

## 3. 信息架构与路由（三个功能 → 四个工作区）

三大功能不是四个页面，而是**四个工作区 + 一个闭环**：

```
①  数据接入 (Ingest)      —— 功能1：上传 → 文件树 → 处理流水线
        │  处理完成
        ▼
②  标的检索 (Search)      —— 功能2：全字段检索 → 标的物全量信息
        │  "以此看关系"
        ▼
③  关系探索 (Explore)     —— 功能3：星图总览 + 五大场景可视化  ★核心
        ▲
        │  "在星图中查看"
④  主体档案 (Party)       —— 任何页点到主体名，落这里看画像
```

### 路由表（Vue Router 4）

| 路径 | 工作区 | 主题 | 说明 |
|---|---|---|---|
| `/ingest` | 数据接入 | 记录域 | 上传 + 文件树 + 处理进度（默认首页） |
| `/search` | 标的检索 | 记录域 | 高级检索 + 标的物全量信息 |
| `/explore` | 关系探索 | 宇宙域 | 星图 + 五大场景（**默认进入总览态**） |
| `/party/:id` | 主体档案 | 记录域 | 主体画像，星图/检索点名字跳这里 |
| `/` | — | — | 重定向到 `/ingest` |

**导航栏顺序即演示顺序**：接入 → 检索 → 探索。演示视频照着点就行，一条直线，不需要来回跳。

### 性能相关：路由级懒加载（必做）

```ts
// web/src/router/index.ts —— three.js 体积大，必须只在进 /explore 时才加载
const routes = [
  { path: '/', redirect: '/ingest' },
  { path: '/ingest', component: () => import('@/views/IngestView.vue') },
  { path: '/search', component: () => import('@/views/SearchView.vue') },
  { path: '/party/:id', component: () => import('@/views/PartyView.vue') },
  { path: '/explore', component: () => import('@/views/ExploreView.vue') }, // 内含 three
]
```

这样首屏（上传页）不背 three.js 的包，首屏更快。`three` 打包后压缩也有 ~150KB+，不做懒加载会白拖慢首屏。

## 4. 功能 1：数据接入工作区（采集台）

### 4.1 交互流程（4 步，每步都有反馈）

```
① 拖入      ② 上传      ③ 入库       ④ 处理
文件区  →  进度条   →  文件树   →  流水线 9 步 + 结果摘要
```

**① 拖入 / 选择**
- 一个大拖拽区，文案明确："拖入一组数据 = 1 个公告 HTML（+ 同名附件 zip）"。
- 支持多个公告批量。每个公告是一个卡片，卡片内显示"公告 + 附件"配对状态（附件可选，赛题里 68 篇公告无附件）。

**② 上传中**
- 每文件独立进度条；总体进度 = 已传字节 / 总字节。
- 校验前置：扩展名白名单（`.html/.zip`）、单文件大小上限、公告必须唯一。
- 失败可单文件重传，不用整批重来。

**③ 入库（后端分配 announcement_id）**
- 后端返回：`announcement_id`（= HTML 文件名去扩展名，如 `t20260202_26139731`）、文件树、附件索引（`a001/a002…`）。
- UI 显示**文件树**：公告为根，附件为子节点；附件节点展示 `display_name / 类型 / 页数 / 可读性`（对应后端附件索引字段）。
- **前端不解析 zip**，树完全由后端给（附件里有嵌套 zip、上千个成员，前端硬解会卡死）。

**④ 处理流水线（这是"异步反馈"的重点，也是你要的 UI 反馈）**
- 展示 9 个步骤，每步一个状态徽标：

| 状态 | 徽标 | 颜色 |
|---|---|---|
| pending | 待处理 | 灰 |
| running | 进行中 | 品红脉冲（**唯一允许的动画**） |
| success | 完成 | 墨黑/金 |
| partial | 部分完成 | 琥珀 |
| skipped | 跳过 | 灰描边 |
| failed | 失败 | 红 |

- 步骤名直接复用后端契约的 `steps[].step`：

  `读入公告 → 理解表格 → 抽候选 → 规划缺口 → 筛附件 → 定页 → 抽附件 → 规范化 → 合并去重 → 检查修复 → 入库`

- 每步可展开看：耗时、失败码（如 `scanned_or_low_text_pdf`）、失败说明。
- 汇总卡片：`项目数 / 标的物数(COB) / 主体数(SUB)` + `是否需人工复核`。
- 完成后两个出口按钮：**去检索这批标的** / **去看这批关系**。

**这样做的理由**：赛题把"处理速率"的计时起点定义为"数据集导入完成时刻"，前端必须让用户**清楚区分「传输」和「处理」两个阶段**——否则演示时观众分不清慢在哪。

### 4.2 数据契约（功能 1）

```ts
// web/src/types/ingest.ts —— 待后端确认后落地

/** 上传一组数据（一个公告 + 可选附件） */
// POST /api/ingest/upload   Content-Type: multipart/form-data
//   files: announcement.html, attachments.zip
export interface UploadResponse {
  announcement_id: string          // 后端分配，= HTML 文件名去扩展名
  announcement_file: FileNode
  attachment_files: FileNode[]
  already_exists: boolean          // 同名公告已存在 → 前端提示 覆盖/跳过/新版本
}

/** 文件树节点（附件元数据来自后端附件索引，前端只渲染） */
export interface FileNode {
  file_id: string                  // a001 / a002；公告为 "a000" 或独立字段
  display_name: string
  kind: 'announcement' | 'attachment'
  extension: string                // .pdf/.docx/.xlsx...
  mime_type: string | null
  page_count: number | null
  text_density: number | null
  readability: 'unknown' | 'text_extractable' | 'low_text' | 'parse_failed' | 'unsupported'
}

/** 触发处理，返回一个 run */
// POST /api/runs  { announcement_id, force?: boolean }
export interface StartRunResponse {
  run_id: string                   // run_<announcement_id>
}

/** 处理进度：直接复用后端 work/runs/<id>/run_state.json 的结构，零额外设计成本 */
// GET /api/runs/{run_id}
export interface RunState {
  run_id: string
  announcement_id: string
  created_at: string
  updated_at: string
  status: 'pending' | 'running' | 'success' | 'partial' | 'failed'
  current_step: string
  steps: RunStep[]
  counts: {
    projects: number
    files: number
    selected_files: number
    selected_pages: number
    html_candidates: number
    attachment_candidates: number
    normalized_candidates: number
    final_cobs: number
    final_subs: number
  }
  review_required: boolean
}

export interface RunStep {
  step: string
  status: 'pending' | 'running' | 'success' | 'partial' | 'failed' | 'skipped'
  output_file: string | null
  started_at: string | null
  ended_at: string | null
  failure_code: string | null
  failure_message: string | null
}
```

> **可选增强（推荐）**：把进度改成 SSE 推送 `GET /api/runs/{run_id}/events`，事件 `{ step, status, ts }`。比轮询实时，且能显示每步耗时。轮询（1.5s 一次）作为兜底即可。

### 4.3 注意事项 & 坑点（功能 1）

- **公告与附件要成组**：赛题是一公告对一 zip。上传 UI 必须让用户自己配对，或按文件名前缀自动配对（如 `t20260202_26126146.html` ↔ `t20260202_26126146.zip`），并允许手动改。
- **重名公告**：`announcement_id` 取自文件名，同文件重传必然撞 ID。要给出明确三选一（覆盖 / 跳过 / 存为新版本），不能静默覆盖。
- **大文件/多附件**：限速 + 超时提示 + 断点续传（可选）。附件里有 86 页 PDF、嵌套 zip，传输时间可能远超处理时间。
- **上传 ≠ 处理完成**：两个阶段分开计时、分开显示。这是评分口径决定的。
- **失败要可读**：`failure_code` 是英文枚举，前端要映射成中文说明（如 `scanned_or_low_text_pdf` → "附件疑似扫描件，暂不支持"），并在需要时提供"查看原始文件"。

## 5. 功能 2：标的检索工作区（高级检索）

### 5.1 "标的物全量信息"到底是什么

这是设计的关键认知：一条标的物记录（COB）的"全量信息"**不是单表的一行**，而是三张表的 join：

```
标的物 (COB)  ← 属于 ←  项目 (Project / 包)
                      ├─ 采购单位 purchaser
                      └─ 中标供应商 subs[is_winner=true]
标的物 (COB)  ── 有 ──  产品供应商 product_supplier（可能是品牌方，不一定投标）
```

所以前端要展示的是一条**扁平化后的视图记录** `CobRecord`，把项目级 + 标的级 + 中标方 + 产品供应商拼在一张卡里，并标明**来源**（来自该公告 HTML 还是哪个附件）。

### 5.2 检索维度（对应"输入中标商/项目名/产品供应商名"）

| 维度 | 控件 | 匹配字段 |
|---|---|---|
| 关键词（全局） | 搜索框 | object_name / project_name / brand / spec_model / 三主体名 |
| 中标供应商 | 主体选择器 | `subs[is_winner].supplier_name` |
| 产品供应商 | 主体选择器 | `cob.product_supplier` |
| 采购单位 | 主体选择器 | `project.purchaser` |
| 项目名称 | 文本 | `project_name` |
| 品目 | 目录树（A/B/C → 2022 目录） | `category_code / category_name / category_type` |
| 品牌 | 文本 | `brand` |
| 金额区间 | 双滑块 | `unit_price` 或 `total_price`（可切换口径） |
| 数量 / 单位 | 数值 + 文本 | `quantity / unit` |
| 来源 | 复选 | `provenance.source_type`（html / pdf / docx…） |

**交互**：顶部筛选栏（可折叠，已选条件以 chip 呈现）+ 中部结果列表（虚拟滚动）+ 右侧详情卡。命中关键词在列表与详情中高亮。支持排序（金额 / 单价 / 相关度）。支持导出 CSV（可直接用作"任务一提取的数据表"提交物）。

### 5.3 数据契约（功能 2）

```ts
// web/src/types/search.ts

/** 检索请求：所有条件可选，后端做 服务端过滤 + 分页 */
// POST /api/objects/search
export interface CobSearchQuery {
  keyword?: string
```

### 5.4 注意事项 & 坑点（功能 2）

- **< 1 秒的敌人是"全量拉取前端过滤"**。必须服务端过滤 + 分页；前端只渲染一屏。列表用**虚拟滚动**（`vue-virtual-scroller` 或自实现），否则 1 万条 DOM 直接卡死。
- **筛选项要防抖**（输入 300ms），金额区间用"确认"再查，避免每拖一次滑块打一次接口。
- **字体大小的取舍**：一屏要塞下 20 行 × 12 列，正文字号不能太大。建议列表 13px、数字 13px 等宽、表头 11px 大写间距。
- **空值要统一显示**：契约里 `null` 表示"原文没有"。UI 显示为灰色 `—`，不要显示 `null` 或空字符串。
- **金额单位**：契约里金额**一律是人民币元**（后端已做万元换算）。前端格式化 `¥1,486,000`，不要再做单位猜测。

## 6. 功能 3：关系探索工作区（★ 核心，含"要不要合并"的正面回答）

### 6.1 结论先说

> **建议：合并成一屏，但不要做成"星图 + 贴着个表格抽屉"那么简单。**
>
> 推荐架构是 **「一个探索台 · 五种场景模板 · 四种交互态」**：
> 星图做主视图，右侧做"叙事面板"，顶部做"场景模板切换"。传统可视化（榜、表、条）**放进叙事面板**，星图与图表**共享同一次查询结果、同一次选中态**。

理由分三层（下面 6.2–6.4 展开）：**信息分工**上二者互补；**评分**上融合能一次覆盖 5 个场景且演示流畅；**工程**上融合能复用同一套查询骨架，代码量小、交互一致。

### 6.2 为什么是"融合"而不是"两张皮"（信息分工）

| 想做的事 | 星图擅长 | 表格/条形图擅长 |
|---|---|---|
| 发现"意外的关系" | ✅ 空间直觉，一眼看出抱团/孤岛 | ❌ 要靠排序逐行读 |
| 读"精确数字" | ❌ 读不出 3 次还是 5 次 | ✅ 精确、可排序、可复制 |
| 看"整体格局" | ✅ 全局密度、聚类 | ❌ 上万行没法看 |
| 比"多个对象" | ❌ 难逐项对比 | ✅ 并排、对齐、差值 |

二者是 **"发现 → 确认"** 的接力：星图负责"我看到了一个可疑的圈子"，表格负责"确认它有 5 次合作、金额 827 万"。拆成两页，用户要在两页之间反复横跳、还要靠记忆对齐"我刚看的是哪个圈"，体验很差。

### 6.3 四种交互态（把"合并"具体化）

```
┌──────────── 探索台状态机 ────────────┐

  Overview(总览)  ──点节点/搜索──▶  Focus(聚焦)
       ▲                              │
       │ 清空                     拖入多个主体
       │                              ▼
     Reset  ◀──────────────────  Compare(对比)
                                      │
                                      │ 点一条结果
                                      ▼
                                  Detail(详情)
```

| 态 | 触发 | 星图 | 右侧叙事面板 | 星图交互 |
|---|---|---|---|---|
| **总览 Overview** | 进入 `/explore` | 全量**采样**星图（不是全量！见 6.7） | 全局统计（节点/关系/公告覆盖面）+ 场景模板选择 | 拖拽旋转 / 滚轮缩放 |
| **聚焦 Focus** | 搜索定位 或 点节点 | 高亮该主体 1–2 跳邻域，其余**淡化** | 该主体画像卡 + **当前场景的排名结果**（榜/表） | 点节点切换焦点，其余不变 |
| **对比 Compare** | 场景 S4/S5 拖入 2..N 个主体 | 只留**交集子图** | 交集表（共同采购单位 / 共同竞标项目） | 交集外的节点统一淡化 |
| **详情 Detail** | 点右侧某条结果 | 该结果相关节点/边脉冲描边 | 下钻到该标的物/项目**全量字段卡**（与功能2 复用同一组件） | 可"在检索页打开" |

**关键：右侧面板不是"星图的附属"，而是"与星图平级的第二叙述通道"。** 二者绑定同一份 `selection`，星图动、面板跟着动，反之亦然。

### 6.4 关于你说的"闪烁 + 隐去 + 右侧展开详细页"

你的直觉基本是对的（这就是经典的 **Overview first → zoom & filter → details on demand**）。但有三处我建议改：

**① 「其余星辰隐去」→ 改为「其余星辰淡化到 18%」，不要真的移除。**
真实移除会破坏**空间记忆**：用户转个身就找不到刚才那颗星了，只能重新搜。淡化（降不透明度）既突出了重点，又保住了"地标"。

**② 「相关公司闪烁」→ 改为「一次性脉冲 + 路径描边 + 排名徽标」，不要无限闪。**

| 原方案 | 问题 | 建议 |
|---|---|---|
| 无限闪烁 | 视觉疲劳、抢注意力、`prefers-reduced-motion` 用户会不适、无障碍差 | 节点做**一次性 600ms 环状脉冲**后静止 |
| 只靠"亮/不亮"区分 | 色盲用户、投影仪偏色都看不出 | 结果节点加 **#1..#5 排名徽标**（形状+数字，不只靠颜色） |
| 相关节点只是一起亮 | 看不出"关系是怎么连的" | 连到焦点的那条**边加粗 + 按合作/竞争着色**，让路径自己讲出来 |

**③ 「右侧展开详细页」→ 分级：面板（默认）→ 大图模式（按需）。**
右侧 340–400px 放得下 TOP5 榜和 8 行表，但放不下 50 行的明细或多表联动。所以：面板里放"摘要级"可视化，需要深看时点"展开"，进入一个**覆盖整个探索台的大图模式**（此时星图暂停渲染以省性能）。

### 6.5 五种场景模板 → 同一骨架，不同"镜头"

这是本方案的核心工程决策：**五个场景不要写五套页面，而是共用一套"查询骨架"，只换输入控件与输出结构。**

统一骨架：`选镜头(场景) → 填主体(1个或多个) → 展开关系 → 得到排序结果 → 图上定位 + 面板呈现`

| 场景 | 输入控件 | 星图表达 | 右侧面板（叙事） |
|---|---|---|---|
| **S1** 采购→合作供应商 | 1 采购单位 | 以采购方为恒星，合作供应商辐射 | **双指标横向榜**（合作次数 / 交易总金额），可切换排序 |
| **S2** 采购→高频投标+协同组合 | 1 采购单位 | 采购方 → 项目 → 投标方 | **TOP5 榜** + **协同组合共现条**（A×B 出现 n 次） |
| **S3** 中标商→共同竞标主体 | 1 中标供应商 | 以该供应商为中心 | **TOP5 榜** + **全部参与主体明细表** |
| **S4** 多中标商→共同采购单位 | 2..N 中标供应商 | 交集子图（多个中心的重叠扇区） | **采购单位交集表**（频次/金额） |
| **S5** 多中标商→共同竞标项目 | 2..N 中标供应商 | 交集项目子图 | **项目表**（项目名/金额/各家是否中标） |

**为什么横向条形榜，不用柱状图？** 主体名是中文长串（"山东新蓝海科技股份有限公司"，15 字）。竖向柱状图的 x 轴标签会斜排/截断；横向条形榜天生适合长标签 + 数值右对齐，读起来快。只有"时间趋势"（按月/年）才需要真正的柱/折线，那属于另一个"统计"视图（见 6.8）。

### 6.6 数据契约（功能 3）

```ts
// web/src/types/explore.ts

export type SceneId = 'S1' | 'S2' | 'S3' | 'S4' | 'S5'

/** 统一场景查询请求：不同场景只是 subjects 个数与 rules 不同 */
// POST /api/scenes/{sceneId}/query
export interface SceneQuery {
  subjects: string[]              // S1/S2/S3 = 1 个；S4/S5 = 2..N 个
  limit?: number                  // 榜单长度，默认 5（TOP5）
  filters?: { date_range?: [string, string]; category_type?: 'A'|'B'|'C' }
}

/** 统一场景查询响应：graph 给星图，narrative 给面板 */
export interface SceneResult {
  scene: SceneId
  elapsed_ms: number              // 便于前端显示"本次查询 xx ms"（对演示很加分）
  graph: {
    nodes: GraphNode[]
    edges: GraphEdge[]
    highlight_ids: string[]       // 需要脉冲/描边的节点
  }
  narrative: {
    title: string                 // 如"广州市增城区中心医院 · 长期合作供应商"
    stats: Array<{ k: string; v: string; unit?: string }>   // 顶部指标对
    ranking: Array<{ rank: number; id: string; name: string; metrics: Record<string, number> }>
    table?: { columns: TableCol[]; rows: Array<Record<string, unknown>> }
    combos?: Array<{ a: string; b: string; count: number }>  // S2 协同组合
  }
}

export interface GraphNode {
  id: string
  label: string
  kind: 'buyer' | 'project' | 'winner' | 'bidder' | 'vendor'
  weight: number                  // 决定星体大小
}

export interface GraphEdge {
  a: string
  b: string
  role: 'win' | 'bid' | 'supply' | 'buy'
  weight: number                  // 决定边粗细/流光密度
}
```

> **统一契约的好处**：后端五种场景都返回同一个 `SceneResult` 形状，前端只需一个渲染器。**加场景 = 加配置，不加代码**。这对"5 个场景每个 4 分"的评分来说，是最省事也最稳的路径。

### 6.7 星图在"全量数据"下的性能策略（对 < 1s 红线至关重要）

赛题基准 1000+ 公告，全量的节点/边可能是**万级**。直接把万级节点丢进 three.js 会：
- 首帧卡顿（>1s）；
- 星云糊成一团，什么也看不出；
- 每帧 CSS2D 标签重排，掉帧。

**策略（必须做）：**

1. **层级化采样（LOD）**：总览态只渲染"权重最高的 N 个"（如采购单位全画 + 项目按金额取前 300 + 主体按出现频次取前 200）。其余以**点云尘埃**示意（有"还有更多"的感觉，不参与计算）。
2. **按需展开**：聚焦某个主体时，只把它的 1–2 跳邻域**补进来**，其余保持尘埃。所以永远不会有"万级全渲染"。
3. **实例化绘制**：同类节点用 `InstancedMesh` 一次 draw call，而不是每个节点一个 Sprite。边同理（用线段批处理）。
4. **动画降级**：`prefers-reduced-motion` 时关掉漂移/呼吸/脉冲，只留静态高亮。
5. **先结果后装饰（对 < 1s 的意义）**：
   - 用户发起查询 → **先渲染右面板的数字与榜单**（纯 DOM，几十毫秒）；
   - 星图**异步**在后台构建（新起一帧 / `requestIdleCallback`），必要时显示骨架。
   - 因为"响应时间 = 前端发起请求至**结果完全渲染完毕**"，而"结果"的核心是数字与清单，不是动画。**让数字先出，就赢下了这 10 分。**

### 6.8 全局统计放哪（一个可选但建议做的加分项）

五大场景都是"以主体为中心"的查询。若想展示**数据总量与分布**（按品目/地区/年份的金额分布），不要塞进探索台的星图，而是做成探索台的一个**独立"统计"标签页**（或一个独立轻量面板），配 ECharts 的柱/折线/饼。理由：分布类图表与关系图是两种不同的"镜头"，混在一起会互相干扰。

> 若引入 ECharts，注意其体积（~300KB+），务必与 three 一样做**懒加载**，只在统计标签激活时才 import。

### 6.9 最小改动兼容做法（若时间紧，想先出能演示的版本）

如果你暂时不想动现有 `RelationsView` 与 `universe.ts` 的结构，**保底方案**是：

- 保留现有 `/relations` 星图页（当"总览"）；
- 新增一个 `/scenes` 页，用表单 + 排行榜/表格实现五个场景；
- 两页之间用"在星图中查看 / 在场景中查看"按钮互跳，参数走 query（`?focus=<entityId>&scene=S3`）。

**代价**：两页各自维护选中态与查询，代码有重复，演示要来回跳；**收益**：改动小、风险低。**建议**：只在"必须两周内能演示"时才走这条路，长期仍走向融合方案。
