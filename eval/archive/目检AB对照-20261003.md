# 目检 A/B 对照：给不给 needs（2026-10-03）

同一批文件、同一提示词，唯一差别是 payload 里有没有 `needs`。三则公告 23 个文件，判定式未切换（影子模式）。

| 指标 | 结果 |
|---|---|
| 对照文件数 | 23 |
| `found_fields` 非空：**无 needs** | **0 / 23** |
| `found_fields` 非空：**有 needs** | **4 / 23**，且与 `needs_hit` 完全一致 |
| 保留/判负翻转 | 1（`包2供应商评审情况表.pdf`：kind `other`→`winner_detail`，skip→parse） |
| 模型调用 | 3 则共 22 次对话调用 + 目检双跑 46 次（含 2 次图像门） |

命中的四例：`B包分项报价表.pdf`→`[brand, spec_model, unit_price,…]`；保险`报价明细附件`→`[total_price]`；
`合同包1：开标记录表.pdf`→`[total_price]`；`包1供应商评审情况表.pdf`→`[total_price]`。

## 结论

1. **不给需求就不报字段**：23 个文件里 `found_fields` 在无 needs 时全为空，有 needs 才出现且与缺口吻合。你说的"目检环节没考虑到确实字段"成立，根因是没人告诉它在找什么。
2. 现行判定式（按 kind）几乎不受影响（23 例只翻转 1 例），说明"切成 `found_fields ∩ needs` 判定"的切换风险主要是**放行数上升**，不是既有结果被推翻。
3. **发现抖动**：同一份扫描件 `劳务报酬表.pdf` 两次跑的置信度分别 0.4/0.9（第一次它让 `low_confidence_keep` 生效、第二次没有）。这解释了上一轮我误报成"needs 导致它转判负"——那是模型抖动不是需求效果。切换判定式之前需要定这个的处理办法（重复目检取多数、或 found_fields 优先于 confidence），我不擅自定。
