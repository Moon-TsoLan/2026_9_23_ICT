# 公告解析与附件目检评估（2026-11-08）

11月9日勘误：源工作簿及冻结快照实际为437条有效标的，原文441表述已更正；原始调用、0/50失败及页决定现场不变。修复后的独立轮次见[分层验证报告](公告前半程修复与分层验证-20261109.md)。

当前版本不能通过运行验收：50则真实API测试中，概要50/50接收成功，正文0/50接收成功，最终成品0/50。主要阻断是正文金额字段协议遗漏。附件隔离实验中，关键扫描报价页得到保留，但多送OCR现象明显，尚不能认定目检方案有效。

本轮只评估。没有修改生产代码、提示词、词表、阈值、预算或数据库，没有调用OCR服务器。不存在修复前后混合计分。

## 1. 试验对象与方法

- 模型：当前生产配置 `deepseek-flash`，既有 `https://api.deepseek.com` 接口。沿用生产调用实现；不在报告保存凭据。
- 公告：冻结历史50例，使用原始HTML，调用当前 `run_announcement`；附件目录显式为空，因此测公告入口及其可达的后半程。新运行目录独立，原成品不覆盖。
- 金标：`50条标注_官方三表_报价补全.xlsx` 的现有冻结快照，98条总表、437条标的、308条投标人。金标包含附件信息，不能将全部金标格直接当成公告可抽取的分母。
- 附件：50例中43例有本地附件，结构盘点共394份。按容器/原生/扫描/混合/长PDF/硬忽略分层，用固定种子20261108选出19份、13则公告；每则至多两份，跨公告相同digest不重复选。选样发生在看模型决定之前。
- 附件样本197个单位：189个原PDF物理页、6个Office本地转换页、2个原生逻辑片段。含3份长PDF各40页预算窗口和5张随机预算外审计页；逻辑片段明确标识，不与物理页混为页数。
- 附件使用现行 `source_pages`、`split_page`、预算选择和 `inspect_page`，不复制一套分流算法。47页实际调用图像目检，原生内容走当前直抽入口的路由；本轮不执行后续附件抽取。
- 由于当前公告入口全部失败，附件条件输入采用固定历史HTML候选，并由当前第3步重新计算一次只读缺口。这是隔离组件实验，不能冒充本版本已成功流转至附件的端到端结果。
- 参考判定另发一次独立提示词调用，提供原页180DPI图像、原生文本、原公告、已知候选及实际缺口，不提供被测决定。参考与被测仍为同一个模型，不是人工金标。原始回答和原文证据全部保存。

未另跑留出集；历史50例中与holdout25已有的2例交叉仍记录在盘点中，没有用留出集选词、调阈值或改提示词。

## 2. 公告解析：入口接收率是首要问题

| 指标 | 本轮结果 |
|---|---:|
| 概要接收成功 | 50/50 |
| 正文接收成功 | 0/50 |
| 正文调用 | 100次，含50次一次修复 |
| 正文拒收尝试：金额性质非法 | 99次 |
| 正文拒收尝试：JSON格式错误 | 1次 |
| 最终公告成品 | 0/50 |
| 实际进入附件处理的公告 | 0/50 |

这不是API网络故障：150次公告API请求均有返回。当前缺陷发生在模型回答与接收协议之间。

`fields.py` 的 `announcement-body-v1` 输出形状含 `amount_kind`，但该步 `STEP_FIELDS` 未列入它，实际加载的字段说明没有 `award/budget/ceiling/unknown` 枚举。概要分支有这项声明。正文模型写出 `winning_amount`、`成交金额`、`agency_fee`、`评审价格`等值，被 `_validate_announcement` 拒收；修复消息只说“金额需要合法的amount_kind”，仍没有补出合法值，第二次继续失败。99次金额校验失败不能折算为99处业务金额读错。

首例 `t20260202_26139731` 的回答已经包含两包、两家中标人及243.131万元、81.9万元，但两次都用“成交金额”作为枚举。正文整路被拒，概要已收到的身份和总额不足以形成采购单元，整则终止。这是本轮实现遗漏，应先修正既有契约接线，不应新增状态、放松成任意枚举或增加兜底调用。

### 拒收前原回答的诊断

为区分“读到了但没接住”和“本来没读出”，另对正文最后一份可解析JSON做只读检查。**没有将它绕过校验送进后半程，也没有计为成功输出。**

| 诊断项 | 字面一致 |
|---|---:|
| 项目名称，按公告计 | 49/50（98.0%） |
| 采购单位，按公告计 | 49/50（98.0%） |
| 公告正文可字面定位的标的名称，独立候选同名 | 311/332（93.7%） |
| 公告正文可字面定位的投标人名称，候选同名 | 306/306 |

名称匹配仅做Unicode/空白规范，投标人和标的允许在同公告候选集合中找同名；没有验证包归属、身份、金额、审查和合并结果。因此306/306不是投标人表正确率，更不是最终全字段准确率。完整金标的437/308行也不是这两个字面子集的分母。

21条标的名称未作为独立同名候选出现，至少有明确的粒度问题：首例“光跳纤架；光熔纤柜”连同两套数量、单价合为一条；后续合并组件以候选编号拆分，无法直接从这一条产生两个独立对象。另有项目名称混入包名、采购单位别名未完整保留等情况。修复枚举之后仍需检查，不能预先认定质量已通过。

## 3. 附件目检：重要扫描页保留，多检集中

47个图像目检页的最终决定：19页拟送OCR、4页使用原生文本、24页跳过。52次API调用包含5次一次修复，没有最终接口或格式失败。

5次修复都是首次选了 `extract` 但页面没有原生文本；一次修复后均改为 `ocr`。这里记录的是现行接口检查的效果，没有自动放大OCR范围。

| 条件指标 | 自动原页参考结果 |
|---|---:|
| 参考认为可补缺口的图像页 | 7页 |
| 上述页面被保留，且选择的读取方式能看到信息 | 7/7 |
| 拟送OCR | 19页 |
| 其中参考认为不能提供当前缺口增量 | 14/19（73.7%） |
| 有缺口增量且原生文本已足够，却仍选OCR | 0页 |
| 保留页中有缺口增量 | 7/23（30.4%） |

7/7样本很小，且参考存在下节所述语义误判，**不能表述为系统100%召回率**。可以确认的是：中卫第2包采购标的3页、德州开标记录2页均被保留为OCR；原生报价明细2页选了extract，没有无谓送OCR。原页复核确认这些扫描表中有报价/标的及续表信息，开标报价阶段仍需下游判断，不能直接等同最终响应报价。

14页疑似多检均来自两份文件：

| 文件 | 本轮可见页 | 拟送OCR | 其中不能补当前缺口 |
|---|---:|---:|---:|
| 广东医科大学委托代理协议 | 6 | 4 | 4 |
| 德州“其他材料.pdf” | 34 | 10 | 10 |

前者多检理由是“属于合同内容，需要OCR”，后者是“属于人员资质，需要识别证书细节”。这些理由没有说明如何补报价、发现投标主体或标的。问题体现为模型把材料类别及“图像中有字”当成继续OCR理由；这不是新增文件名过滤词的依据。

## 4. 覆盖不能只看目检保留率

129个单位属于原生直抽路由，其中自动参考认为42个有缺口增量、87个没有。这87个包括重复证据、空表/模板、通用条款等。**它们没有被送OCR**，因此不能算OCR多检；但说明“取消原生预览判断”后，抽取调用本身仍有成本。本轮未执行附件抽取，不能用参考调用的token冒充生产抽取成本。

3份长PDF实际分别为108、53、82页，合计243页：本轮看了各40页预算内窗口加各5页预算外审计，共135页。其余108页没有核对，绝不按无用页计入。

- 15张预算外抽查页中，参考发现1张描述性相关页：离退休干部数据治理磋商文件物理第20页，包含网络安全等级保护测评技术项。原生文本可读，但没有进入冻结40页窗口。它不是已确认漏掉一条独立成交标的。
- 按现行顺序模拟每文件30个抽取上下文，另有顺义招标文件第44、46、47页的相关描述进不了抽取窗口。属于预算覆盖损失，不能归为模型skip。OCR后产生的实际片段数未知，因此该模拟仅是可达上限。
- 硬忽略的声明函确有制造商证据；参考把其中两页当成“发现新投标人”是角色混淆。它说明硬忽略会放弃部分产品供应商信息，不能据此宣称已确认漏了投标人，也没有据此改动这条冻结规则。
- 每则只抽取至多两份附件，没有复现该公告全部文件的100上下文竞争，不提供全公告预算后的覆盖率。

自动参考的原始宽口径汇总为：52个有缺口增量单位，路由可读49/52，每文件预算后46/52。**这些数字只保存在可复算诊断中，不作为验收正确率**：参考有预算当成交计量、制造商当投标人、已知名称/技术描述当新增对象等误判，且未覆盖全部预算外页面。

## 5. 参考判定自身的误差

本轮专门保留反例，没有把复核模型当成真值：

1. 图书馆报价模板：40000元的列名明确为“最高限价”，响应报价和单价仍是占位符。参考声称可为成交 `total_price` 提供依据，不成立。
2. 中小企业声明函：佛山凯悦、南京极域等在原文身份是制造商，标的名称也已在公告中。它们可以补产品供应商，但不构成新投标主体。
3. 梓瑞报价明细：制造商名称确有业务增量，但当前needs没有该描述字段缺口。参考将“任何新业务值”和“能补当前任务缺口”混在一起。

这三类问题不影响“50例正文全部拒收”的确定性结论，也不改变两份无关文件产生14页拟OCR的实证；会影响精确的全字段覆盖率分母。后续验收应使用独立人工页标注，并分别标识信息存在、是否新增、字段角色与金额性质，不按本次反例调词表或阈值。

公告单则耗时中位10.25秒、最大51.52秒；主批次181.96秒（首例已在smoke调用缓存中，不计入该批次墙钟，表中token仍计入首例）。这都是失败入口的耗时，不能代表完整流程速度。API返回的缓存命中/未命中token也已逐请求保存。

没有实际OCR请求、OCR耗时、OCR费用或OCR后抽取结果；没有与旧流程做等条件实验，也没有账单金额。因此不能认定当前方案总耗时/费用已改善，不能仅凭拟OCR页数少于可见页数宣布成功。

## 7. 结果可信范围及后续优先级

确定结论：当前公告正文的字段协议接线使这50则全部失败；附件模型在固定条件下保住了所测关键扫描表，但对委托协议、人员资质产生明显多检；预算覆盖与模型决定必须分开看。

处理优先级已归入唯一待办清单，不在本报告实施：先补齐正文已有 `amount_kind` 声明并用本轮真实失败回答回放；再检查并列标的粒度、身份/包归属及最终字段正确率；附件用人工独立页标签确认多检与预算损失。修复不需要新增统一state、复核阶段或自动扩大OCR。真实OCR链路与总费用/耗时验收待解析服务器恢复。
